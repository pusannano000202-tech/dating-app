## 4. 예약 요청이 어느 사장님 계정으로 가는가

**Git 브랜치끼리 요청을 주고받는 것이 아니다. 실행 중인 앱이 공통 서버/DB의 예약을 읽고 쓴다.**

```text
유저 화면: 예약할 업장 선택 (venue_id)
  → 공통 서버: 예약 대표권·동행 동의·요청 조건 검사
  → 그 업장 ID에 묶인 예약 요청/단위 저장
  → 현재 활성화된 업장 membership + 요청 수신 권한 조회
  → 해당 업주의 요청함 + 허용된 직원의 요청함 / 개인 알림
  → 업주 로그인 계정으로 수락·부분 수락·변경 제안
  → 서버가 업장 권한·기한·revision·중복 예약 재확인
  → 같은 예약 원장 갱신
  → 해당 예약 참가자에게 결과 안내
```

- 요청의 목적지는 사용자 계정 이름/전화번호가 아니라 `venue_id`다. 가게 이름이 같아도 다른 ID면 별개 가게다.
- `venue_partner_memberships`의 활성 연결과 업무 권한으로 수신자를 구한다. 사용자 앱이 `recipient_user_id`나 사장님 이메일을 임의 지정하지 않는다.
- 여러 직원에게 알림이 가더라도 예약은 한 건이다. 먼저 처리한 결과를 나머지 화면에도 반영한다.
- 퇴사/회수/업장 정지 계정은 알림 발송 시와 조회·수락 시 다시 제외한다. 이미 받은 알림을 눌러도 권한을 되살리지 못한다.
- 담당자가 없거나 전부 비활성인 업장은 정상 접수된 것처럼 표시하지 않는다. 예약 접수 불가/운영 확인 대상으로 분리하고 엉뚱한 관리자 계정에 대신 배정하지 않는다.
- 운영 관리자 문제 알림과 업주 예약 수락 권한은 별개다. 개발을 맡았다는 이유로 성준 개인 계정에 모든 가게/최고관리자 운영 권한을 부여하지 않는다.
- 서버 저장 성공, 알림 대기열 저장, 푸시 전송, 실제 수신/읽음, 예약 확정은 서로 다른 상태다. 푸시 실패로 예약을 중복 생성하지 않는다.

## 5. 양쪽이 맞출 전달 계약 초안

이는 **새 API 설계안**이며 현재 실행 가능한 endpoint/DTO라고 가정하지 않는다. 구현 전 공용 담당자가 확정·테스트한다.

| 값/동작 | 의미 | 권위 있는 작성자 |
| --- | --- | --- |
| `reservation_id` / 요청·동행 단위 ID | 화면/업장/알림에서 같은 예약 식별 | 서버 생성 |
| `venue_id` | 요청할 제휴 업장 | 사용자/운영 선택 후 서버 검증 |
| `source_kind`, 원본 ID | 매칭·보이스·리그·모임 중 어디서 왔는가 | 서버가 원본 접근 권한 확인 |
| 동행 단위별 참여자/인원 | 실제 동의한 팀 또는 한 일행 | 서버 멤버십/동의 스냅샷 |
| 요청·제안·확정 시간 구간 | 최초 19시, 제안 19시30분, 실제 확정은 별도 | 서버 저장·revision 갱신 |
| 상태와 `revision` | 오래된 화면/알림으로 덮어쓰지 않기 위한 버전 | 서버 |
| `idempotency_key` | 재전송해도 같은 요청/수락 한 번만 처리 | 호출별 고정 키 + 서버 검증 |
| `team_code`, 좌석 배정 | 퀀텀 A팀과 테이블 연결 | 서버 식별자 + 권한 있는 업장 배정 |

시간은 API에서 오프셋 포함 ISO 시각, 표시 시간대는 `Asia/Seoul`로 합의하는 안이다. 화면·알림의 시간을 하드코딩하거나 서로 다른 프론트엔드에서 재계산해 확정값을 만들지 않는다.

새 API의 의미 단위: 요청 생성/조회/취소, 업장별 받은 요청 목록, 부분 수락/거절/변경 제안, 참가자 변경 확인, 좌석 배정, 방문 확인, 기간별 실적 조회. 상세 route·payload·오류 코드는 공용 모듈에서 한 번 정하고 양쪽이 같은 계약 시험을 사용한다.

필수 결과: 미로그인, 다른 업장/예약 접근, 오래된 revision, 요청 만료, 자리 중복, 동행 정보 변경, 권한 회수, 알림 전송 실패를 구분한다. 다른 가게 존재 여부·개인 정보를 오류 메시지에 노출하지 않는다.

## 6. 담당 경계 — 브랜치만 나누면 끝이 아닌 이유

| 영역 | 주 담당 | 다른 쪽이 지킬 경계 |
| --- | --- | --- |
| 업장 예약함·테이블/시간표·실적·관리자 UI | 성준 | 사용자는 시안/요구를 공유하고 같은 파일을 동시 수정하지 않음 |
| 사용자 매칭·보이스·리그·모임 진입·예약 카드 | 사용자 앱 담당 | 성준은 사용자 화면을 임의 교체하지 않음 |
| 공통 예약 API/타입/DB/RLS/알림·금융 연결 | **공용 변경 담당자 1명 지정 필요** | 별도 버전으로 각자 구현 금지. 해당 묶음의 소유 파일과 계약 먼저 합의 |
| 인증 핵심·root layout·package/lock·배포 설정 | 공동 보호 파일 | 영향 확인 없이 양쪽이 동시에 수정하지 않음 |

성준은 업장/관리자 화면을 맡는다. 특정 공용 서버 묶음까지 맡길지는 별도 명시하고 담당자 지정 전에는 새 운영 schema나 양립 불가능한 공용 타입을 만들지 않는다. mock 화면과 테스트 설계는 병행 가능하다.

- 브랜치는 코드 작업을 나눌 뿐 DB를 자동 분리하지 않는다. 서로 다른 브랜치에서 같은 운영 DB를 사용하면 여전히 충돌한다.
- 개발 초기에는 각자의 로컬/승인된 테스트 DB를 사용한다. 통합 시험은 동일 코드 계약·migration 버전의 전용 테스트 환경에서 수행한다.
- 공통 서버 변경은 작은 검증 단위로 공유하고 양쪽에 먼저 반영한 뒤 UI를 연결한다. 변경 합치기는 main에 바로 하지 않고 별도 통합 후보에서 검증한다.
- GitHub는 코드 전달이고 실시간 같은 화면 공유가 아니다. 함께 디버깅할 때는 화면 공유나 권한 제한된 개발 서버 공유가 별도로 필요하다.
- 처음에는 사용자 요청→업장 수락 한 건을 두 계정으로 확인하는 작은 공동 시험부터 한다. 전체 계정/운영키를 공유하지 않는다.

## 7. 성준이 받는 방법

새 폴더에 받는 경우:

```sh
git clone --branch "codex/성준-업장-퀀텀" https://github.com/pusannano000202-tech/dating-app.git quantum-partner
cd quantum-partner
```

기존 clone을 쓰면 먼저 미커밋 작업을 확인하고 보존한다. 깨끗하며 같은 이름의 로컬 브랜치가 아직 없을 때만:

```sh
git fetch origin
git switch --track "origin/codex/성준-업장-퀀텀"
```

이미 해당 로컬 브랜치가 있으면 새로 만들거나 강제 덮어쓰지 말고 상태를 확인한다. `reset --hard`, `clean`, `force push`로 맞추지 않는다.
Node/설치/테스트 Auth/3010 실행 방법은 기존 공유 안내를 따른다. 포트 번호는 저장소나 서버 권한이 아니다. 각자의 `localhost:3010`은 자기 PC다. 같은 테스트 서버/DB를 볼 때만 같은 예약 데이터가 보인다.

비밀키·`.env.local`·쿠키·실제 업장 초대 토큰·운영 계정 자료는 이 공개 저장소에 넣지 않는다. 테스트 자격 증명은 승인된 별도 안전한 채널로 전달한다. GitHub write 권한은 별도 계정별 권한이며 브랜치 이름을 만드는 것만으로 생기지 않는다. 성준 GitHub ID/초대 수락 여부는 이번에 확인하지 않았다.

## 8. 성준에게 전달할 메시지

> 성준아, 업장·관리자 쪽은 `codex/성준-업장-퀀텀`, 사용자 쪽은 `codex/유저-퀀텀`에서 작업하면 돼. 두 브랜치 모두 기존 앱 전체와 업장/관리자 초안이 들어 있어. 이 문서와 연결된 공통 예약 계획부터 봐줘. 새 방향은 미리 받을 팀 수를 입력하는 방식이 아니라, 퀀텀이 팀·인원·시간을 요청하면 업장이 전부/일부 수락하거나 시간 변경을 제안하는 방식이야. 업장은 테이블 배치와 시간표에서 퀀텀 A/B/C팀을 관리하고, 사용자는 같은 예약의 시간·장소·좌석 안내를 봐야 해. 신규 공통 예약은 아직 구현 전이니까 기존 사람 매칭·채팅·보증금은 유지하고, 공용 API/DB 담당과 계약을 먼저 맞추자. 운영 DB·main·배포는 아직 건드리지 말아줘.

이 메시지는 전달용 초안이다. GitHub 게시가 성준에게 메신저/이메일로 직접 전달됐거나 성준이 읽었다는 뜻은 아니다.

## 9. 첫 공동 검수 체크리스트

- 두 계정이 같은 테스트 DB/예약 버전을 읽는가? 별도 테스트 업장 membership을 사용했는가?
- A업장 요청이 A업주/허용된 직원에게만 보이고 B업주는 접근할 수 없는가?
- 5팀 중 3팀 수락 시 총인원·미수락 2팀 상태가 양쪽에서 일치하는가?
- 19시→19시30분 제안 알림과 최종 확정 알림이 구분되는가? 확인 전 확정 표시가 없는가?
- 테이블 시간표에서 중복 배정이 차단되고 사용자 좌석 카드와 같은 revision인가?
- 방 종료 뒤 예약 유지, 대표자 변경, 업장 취소·권한 회수, 늦은 수락·중복 클릭을 처리하는가?
- 옛 자동 작업이 새 예약을 취소/환불하지 않는가? 실제 결제·환불은 미승인 상태로 닫혀 있는가?

이 문서와 계획 공유만으로 위 기능이 통과한 것은 아니다. 현재 코드/운영 미완료 경계는 기존 공유 보고와 공통 예약 계획을 따른다.
