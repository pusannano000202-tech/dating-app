# 성준 업무 전달 — 퀀텀 업장 기능 요구사항

작성: 2026-09-21 KST. 이 문서는 구현할 기능과 검수 기준을 전달한다. **이번 공유는 문서 변경이며 신규 업장 기능의 구현·DB 적용·실제 예약·배포 완료 보고가 아니다.** 디자인은 성준 담당이며 이전 관리자 시안의 색상·배치를 그대로 구현할 의무는 없다.

## 1. 먼저 지킬 제품 기준

- 업장/관리자 작업의 기존 공유 브랜치는 `codex/성준-업장-퀀텀`이다. 사용자 브랜치와 main을 덮어쓰거나 사용자 화면을 삭제하지 않는다.
- **첫 연결 범위는 학과대항전 뒤풀이**다. 보이스·오늘밤·일반 모임으로 자동 확대하지 않는다.
- 기존 팀 채팅에서는 우리 편, 양 팀 경기 채팅에서는 해당 방의 허용 참가자끼리 초대한다. 그 방에 현재 참여 권한이 있는 사람은 주장 여부와 관계없이 제안할 수 있다.
- 초대자가 기존 채팅에서 희망자와 날짜·시작/종료 시간·장소를 협의한다. 각자 참여 의사를 밝히고 최종 조건에 본인이 동의한 사람만 예약 인원에 포함한다.
- 연결된 **카페·보드게임·술자리** 중에서 고른다. 관리 화면의 볼링 등 추가 분류는 후속 확장 요구이며 현재 뒤풀이 API 지원으로 간주하지 않는다.
- 업장은 요청한 조건 그대로 **수락/거절**한다. 이번 뒤풀이에는 다른 시간 제안, 일부 인원만 수락, 동의 없는 장소 변경을 넣지 않는다. 조건/참여자가 바뀌면 사용자 쪽에서 다시 동의받는 절차가 필요하다.
- GPS 추적·GPS 도착 인증은 제품에서 제외한다는 사용자 결정이다. 기존 앱 전체의 GPS 코드 제거까지 완료됐다는 뜻은 아니다.
- 개인 정산은 실제 참석자와 결제자 사이의 기록이다. 업장에 개인 정산 상세를 제공하거나 보증금에서 자동 차감하지 않는다.

9월 20일 [공통 인수인계](QUANTUM_USER_PARTNER_HANDOFF_2026-09-20.md)의 부분 수락·시간 변경·공통 담당 미정 설명보다 **이 문서의 학과대항전 뒤풀이 규칙과 아래 공통 담당 지정이 우선**한다. 다른 제품까지 같은 방식으로 바꾸라는 결정은 아니다.

## 4. 양쪽 연결 계약과 책임

```text
사용자: 기존 채팅의 초대 → 각자 참여 → 조건 협의 → 각자 최종동의 → 요청
공통 서버: 방 권한·동의 버전·업장·인원·시간 확인 → 같은 초대/예약 기록 저장
업장: 해당 venue_id의 유효 권한 계정만 조회 → 동일 조건 수락 또는 거절
사용자: 같은 예약 기록의 결과 표시 → 기존 채팅에서 약속 확인
```

- 성준 담당: 업장 요청함/응답/프로필/관리자 UI와 디자인. 공통 타입·DB를 각자 별도 버전으로 만들지 않는다.
- 사용자 앱 담당: 기존 사용자 화면 연결 및 **학과대항전 뒤풀이 공통 API·DB 권한·알림 저장**. 다른 관리자 신기능 API까지 담당이 자동 확정되는 것은 아니며 업무 착수 시 소유 파일을 지정한다.
- 서버 목적지는 `venue_id`이며 현재 활성 업장 membership으로 요청 수신자를 찾는다. 개발자 성준의 계정이나 Git 브랜치가 예약 수신처가 아니다.
- 브랜치를 나눠도 DB는 자동 분리되지 않는다. 연동 시험은 계약/DB 버전이 일치하는 별도의 승인된 테스트 환경에서 서로 다른 사용자·업장 세션으로 한다.

### 별도 로컬 구현의 API 연결 요약 — 아직 이 공유 브랜치에 없음

| 항목 | 현재 로컬 계약 | 주의 |
| --- | --- | --- |
| 요청 조회 | `GET /api/partner/league-afterparty?venue_id=...` | 현재 로그인 세션과 해당 업장 권한 필요. |
| 응답 처리 | `PATCH /api/partner/league-afterparty` | `venue_id`, `invitation_id`, `expected_version`, `reply`, `idempotency_key`. reply는 `accepted` 또는 `rejected`. |
| 계정 전환 방어 | 현재 계정 UUID를 `X-Expected-Account` 헤더에 전달 | 헤더 자체가 인증은 아니다. 서버 인증 결과와 일치 및 업장 권한을 검사한다. |
| 동시성 | version/동의 revision, 같은 요청의 멱등 키 | 결과 불명확 시 최신 조회와 동일 요청의 동일 키 재시도. 409를 새 요청이나 자동 수락으로 바꾸지 않는다. |
| 반환 정보 | 요청 ID·버전·장소·시간·활동·동의 인원·상태 등 최소 정보 | 연락처/방 전체 대화/개인 정산 원장을 업장에 자동 제공하지 않는다. |
| 오류 | 미로그인/권한 없음/요청 변경/만료/연결 불가를 구분 | 실제 공유된 공통 타입과 HTTP 응답을 기준으로 연결하며 이 요약만으로 DTO를 새로 만들지 않는다. |

현재 로컬 알림의 업장 도착 경로 `/partner`에는 대응 루트 페이지가 없다. 기존 `/partner/tonight`가 새 뒤풀이 화면을 대신하지 않는다. **새 요청함의 실제 route를 정하고 알림 도착 경로와 함께 연결하는 것이 1차 필수 작업**이다. 인앱 이벤트 저장 외 실제 휴대폰 푸시는 미검증/미연결로 남긴다.

## 5. 성준에게 요청하는 첫 결과물

1. STORE-01~06의 화면 목록과 클릭 가능한 모바일/데스크톱 시안. 목업 데이터는 명확히 표시한다.
2. 사용할 기존 파일과 새 파일의 목록. 사용자·공통 보호 파일에 영향이 있으면 수정 전에 공유한다.
3. 서버 연결 전 모의 상태: 새 요청/수락됨/거절됨/만료/중복 처리/권한 회수/연결 실패. mock 통과와 실제 연결 통과를 분리한다.
4. 공통 코드 전달 뒤, 사용자 최종동의 → 정확한 업장 수신 → 수락/거절 → 사용자 상태 일치까지 같은 테스트 예약으로 검증한다.
5. 보고에는 브랜치·commit, 수정 파일, 실제 캡처, 수행 테스트, 남은 미검증을 쓴다. 연락처·쿠키·초대 토큰이 담긴 캡처는 올리지 않는다.

## 6. 배포 전 별도로 닫을 항목

- 공통 뒤풀이 소스의 검토·commit/push 및 양쪽 적용. 이번 문서 게시와 별개다.
- 필요한 migration의 적용 승인과 실제 환경 확인. 기존 데이터 초기화로 해결하지 않는다.
- 참가자 변경/대표자 이탈/업장 수락 후 취소/미응답 처리 정책과 복구 담당.
- 다른 업장 계정·회수 계정의 접근 거부, 재시도·동시 처리, 기존 채팅과 예약 이력 보존 시험.
- 실제 예약 전송·운영 DB·실제 돈 이동·main 병합·배포는 각각 승인 후 진행한다.

이 문서의 게시 또는 Slack 발송은 담당자의 열람·착수·구현 완료를 의미하지 않는다.
