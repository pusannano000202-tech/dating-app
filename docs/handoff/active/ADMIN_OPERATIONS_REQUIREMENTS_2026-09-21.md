# 관리자 퀀텀 — 학교별 운영 기능·성준 인수인계

작성: 2026-09-21 KST. 대상: 관리자 화면 담당 성준, 공통 서버 담당자, 업무 조정 담당자.
목적: 학교별 사용자·업장 운영에 필요한 기능과 완료 기준을 전달한다. **이번 전달물은 요구사항 문서이며 구현 완료본이 아니다.**
디자인은 성준이 담당한다. 앞서 본 관리자 시안은 구조 참고이며, 색상·배치·상호작용이 최종 승인된 디자인은 아니다.

## 1. 범위와 우선순위 규칙

- 사용자 확정 방향: 학교 선택, 사용자/업장 전환, 일정별 모임 운영, 업장 등록·담당 계정 연결, 필요한 참가자 연락·상태 확인.
- 아래 세부 역할, 큐 구성, 처리 단계는 이 방향을 안전하게 구현하기 위한 요구·권장 설계다. 기존 DB 컬럼이나 API 상태명으로 확정됐다는 뜻이 아니다.
- 학과 대항전 뒤풀이의 최신 흐름은 **기존 채팅 초대 → 본인 참석 선택 → 장소·시간 합의 → 조건 확인 → 업장에 요청 → 동일 조건 수락/거절**이다.
- 제안자는 해당 채팅방에서 제안 권한이 있는 참가자다. 주장만 가능하게 제한하거나 다른 사람을 임의 참석 처리하지 않는다.
- 학과 대항전 뒤풀이에는 업주의 다른 시간 역제안 기능을 넣지 않는다. 조건 변경 시 필요한 참가자에게 다시 동의를 받는다.
- GPS는 제품 흐름에서 제외하기로 했다. 이 결정은 저장소의 기존 위치 관련 코드가 모두 제거·검증됐다는 증거가 아니다.
- 현재 뒤풀이 카테고리는 카페·보드게임·술자리다. 볼링장 등은 업장 카탈로그 확장 요구이며 현재 뒤풀이 API 지원 완료로 표시하지 않는다.
- [기존 공통 인수인계](QUANTUM_USER_PARTNER_HANDOFF_2026-09-20.md)는 보존한다. 그 문서의 시간 변경·부분 수락 안을 학과 대항전 뒤풀이에 자동 적용하지 않는다. 다른 예약 상품의 정책까지 임의 변경하지 않는다.
- 이번 문서 공유에 코드 구현, 공용 계약 변경, DB 적용, 실예약, 결제, main 병합, 배포 승인은 포함되지 않는다.

## 2. 관리자 화면 구조

```text
학교 선택: 부산대 / 연세대 / 고려대 … (담당 권한이 있는 학교만)
  ├─ 오늘 할 일: 처리할 문제와 담당자·기한
  ├─ 사용자: 일정·모임 / 참가자 확인 / 신고·문의
  └─ 업장: 카테고리·업장 / 등록·권한 / 예약 요청·예외 / 실적
```

- 학교 선택은 화면 필터만이 아니다. 목록·상세·검색·내보내기·변경 요청 모두 서버에서 학교 접근 권한을 검사한다.
- 선택 학교를 바꾸면 이전 학교의 선택 항목, 열린 상세, 검색 결과, 처리 대상 및 지연 응답을 제거하거나 무효화한다.
- 한 업장이 여러 학교를 서비스할 수 있다. 같은 매장을 학교마다 복제하지 않고 업장과 서비스 학교의 연결을 관리한다.
- 최고관리자의 전체 학교 조회와 학교 운영자의 담당 학교 조회를 구분한다. 개발 담당이라는 이유로 운영 권한을 자동 부여하지 않는다.
- 학교·업장 관리 기능은 오늘밤 모집 회차 유무와 독립적으로 접근할 수 있어야 한다.

## 3. 사용자·현장 운영 기능

### ADM-01: 오늘 할 일과 일정별 운영

- [ ] 업장 미응답, 담당 계정 없음, 참석 미확인, 처리할 신고, 초대 승인 대기, 알림 실패를 우선순위·담당자·기한으로 표시한다.
- [ ] 날짜를 선택하면 그날 모임 종류·시간·팀·예약 상태·예정 인원·확인 인원·문제 건수를 볼 수 있다.
- [ ] 모임을 누르면 해당 모임 참가자와 예약 상세로 이동한다. 전체 개인정보를 처음부터 한 화면에 펼치지 않는다.
- [ ] 처리 시작·담당 변경·완료·재개 이력을 남겨 두 운영자가 중복 연락하거나 서로 다른 결정을 덮어쓰지 않게 한다.
- 완료 기준: 회차가 없는 날에도 업장 등록·신고 처리가 가능하고, 학교를 바꾼 직후 이전 학교의 지연 응답이 표시되지 않는다.

### ADM-02: 참가자 검색·연락·참석 확인

- [ ] 별명·회원 ID 등 허용 검색 기준으로 찾고, 소속·계정 상태·관련 모임·예약·신고·연락 이력을 필요한 범위에서 확인한다.
- [ ] 참석 상태를 미확인 / 참석 확인 / 불참 확인 / 사전 취소 등으로 구분한다. 정확한 상태명은 공통 계약에서 합의한다.
- [ ] 전화번호는 기본 마스킹하고, 권한 있는 담당자가 관련 업무와 사유를 선택한 경우에만 필요한 범위를 열람한다.
- [ ] 누가 언제 왜 연락처를 봤는지, 연락 결과와 참석 확인 근거·수정 사유를 남긴다. 자유 입력란에 불필요한 개인정보를 복사하지 않는다.
- [ ] 답이 없다는 사실을 노쇼로 확정하지 않는다. 연락 실패와 불참 확인을 구분하며 잘못된 기록을 정정할 수 있게 한다.
- [ ] GPS로 참석 여부를 판단하지 않는다. 임의의 위치 수집·위치 인증 버튼도 추가하지 않는다.
- 완료 기준: 비담당 학교·권한 없는 계정의 연락처 접근이 서버에서 차단되고, 미응답만으로 제재·보증금 차감이 실행되지 않는다.
- 운영 전 미결정: 연락 목적·허용 역할·보관 기간·삭제 기준·이용자 안내. 여기서 법적 적합성 검토가 완료됐다고 주장하지 않는다.

### ADM-03: 신고·문의·이의 처리

- [ ] 접수 → 담당 배정 → 사실 확인 → 처리 → 결과 안내 → 필요한 이의 검토의 진행 상태와 근거를 남긴다.
- [ ] 관련 모임·예약·메시지 등 필요한 자료로 범위를 제한한다. 관리자에게 모든 개인 대화를 무제한 공개하지 않는다.
- [ ] 신고자 신원을 상대방에게 자동 공개하지 않으며, 신고 접수만으로 자동 제재하지 않는다.
- [ ] 제재 대상·사유·기간·해제·이의 처리 권한을 분리하고 취소·정정 기록을 보존한다.
- 완료 기준: 신고 조회와 조치에 별도 권한 검사가 있고, 사건과 무관한 사용자 자료를 API 직접 호출로 얻을 수 없다.

## 4. 업장 관리 기능

### ADM-04: 업장 등록·카테고리·프로필 공개

- [ ] 카테고리와 서비스 학교로 업장을 찾고, 지점·주소·연락 수단·사진·소개·영업일·휴무·예약 가능 시간·수용 조건을 관리한다.
- [ ] 기존 업장과 중복인지 확인하고 새 업장을 생성한다. 이름만 같은 다른 지점과 같은 지점의 다학교 연결을 구분한다.
- [ ] 초안 / 검토 필요 / 공개 가능 / 신규 접수 중지 등 운영 상태를 구분한다. 공통 계약 합의 전 별도 DB 상태를 임의 추가하지 않는다.
- [ ] 확인된 업주와 필수 프로필을 갖춘 업장만 사용자 노출 대상으로 삼는다. QR 진입·작성 완료만으로 즉시 공개하지 않는다.
- [ ] 필수 누락·사용자 화면 미리보기·최종 수정자를 보여 준다. 영업시간과 실제 예약 가능한 시간·정원은 별도로 검사한다.
- [ ] 주소·가격·시간·취소 조건을 바꿔도 이미 확정된 예약의 약속 내용을 조용히 덮어쓰지 않는다.
- 완료 기준: 미승인 업장은 사용자 목록에서 숨겨지고, 업장 수정 후에도 기존 예약의 확정 시점 조건을 재현할 수 있다.

### ADM-05: QR 초대·계정 연결·회수

- [ ] 특정 업장에 연결된 초대 생성·만료·재발급·폐기 기능을 둔다. QR은 그 초대로 진입하는 수단이지 권한 증명 자체가 아니다.
- [ ] 로그인 → 대상 계정·초대 조건 확인 → 본인 수락 → 필요한 관리자 승인 → 활성 권한 연결 순서를 지킨다.
- [ ] 기존 대상 계정 지정 방식과 새 사장님 가입 방식의 차이를 공통 담당자와 정한다. 누구나 QR만 스캔하면 업주가 되는 흐름은 금지한다.
- [ ] 직원은 본인 계정을 사용한다. 조회·수락·프로필 수정·직원 관리 권한을 업무별로 구분한다.
- [ ] 퇴사·권한 회수 즉시 조회·처리·새 알림 수신 대상에서 제외한다. 오래된 알림 링크로 권한이 복원되지 않게 한다.
- [ ] 신규 예약 접수 중지, 사용자 목록 숨김, 계정 권한 회수, 제휴 종료는 서로 다른 작업으로 다룬다.
- [ ] 마지막 담당 계정이 없어질 때 기존 예약과 미처리 요청을 운영 예외로 넘긴다. 예약·감사 기록을 삭제하지 않는다.
- 완료 기준: 만료·폐기·재사용 초대, 다른 계정, 다른 업장 ID 요청을 거부하며 회수 직후 열린 화면의 처리도 거부한다.

## 5. 예약·알림·금융 운영

### ADM-06: 예약 요청과 예외 대응

- [ ] 공통 예약 ID로 학교·출발 채팅/모임·업장·요청 시간·동의 인원·조건 버전·요청 시각·현재 상태·다음 담당 행동을 확인한다.
- [ ] 동행 확인 중, 요청 대기, 업장 수락, 거절, 취소, 방문 확인을 구분한다. 안내 문구를 실제 서버 상태로 오인하지 않는다.
- [ ] 실제 활성 업장 담당 계정으로 요청이 전달되는지 검사한다. 이름·전화번호·개발 담당자의 계정으로 목적지를 추측하지 않는다.
- [ ] 미응답·중복 클릭·업장 휴무·담당자 회수·제안자 이탈·참석자 변경을 예외 큐로 관리하고 해결 주체와 기한을 표시한다.
- [ ] 학과 대항전 뒤풀이는 동의한 사람만 포함한다. 관리자가 모두의 동의를 대신 입력하거나 업주의 시간 역제안을 확정으로 바꾸지 않는다.
- [ ] 장소·시간·인원 등 동의에 영향을 주는 조건이 바뀌면 정책에 따라 재확인한다. 오래된 버전으로 수락·신청하지 못하게 한다.
- 완료 기준: 같은 요청을 반복해도 예약이 중복 생성되지 않고, 거절·취소·조건 변경이 사용자와 업장에 일관되게 보인다.

### ADM-07: 알림 실패와 실제 전달 상태

- [ ] 사건 발생, 알림 기록 생성, 발송 대기, 발송 결과, 확인 가능한 수신·읽음 증거를 구분해 운영자에게 표시한다.
- [ ] 푸시를 받지 못해도 앱 요청함에서 원본 상태를 조회할 수 있게 하고 실패 재처리가 예약을 재생성하지 않게 한다.
- [ ] 중복 알림·누락·잘못된 수신자를 조사할 사건 ID와 처리 이력을 남긴다. 민감한 연락처·신고 내용은 푸시 본문에 넣지 않는다.
- 완료 기준: 알림 저장 성공만으로 휴대폰 수신 완료라고 보고하지 않으며 실제 기기·알림 허용/거부 조건을 별도 검증한다.

### ADM-08: 세 가지 금전 기록 분리

| 기록 | 관리해야 하는 내용 | 혼동하면 안 되는 것 |
| --- | --- | --- |
| 보증금 | 원결제·반환 요청·취소 처리 중·성공/실패·확인 근거 | 요청 접수는 실제 반환 완료가 아님 |
| 참석자 개인 정산 | 정산 대상·금액·보냈다는 표시·받은 사람의 확인·이견 | 자기 신고는 실제 송금 증거가 아님 |
| 업장 실적 | 예약 인원·실제 방문 확인·추정 금액·확인된 매출 근거 | 예약 합계는 실제 매출·수수료·정산액이 아님 |

- [ ] 보증금은 합의된 Toss 원결제 취소 방식과 기존 보안 경계를 유지한다. 다른 계좌 임의 지급 기능을 새로 만들지 않는다.
- [ ] 전화 결과·참석 상태 수정만으로 보증금 차감 또는 실제 취소를 자동 실행하지 않는다. 금융 처리 권한·검증을 별도로 둔다.
- [ ] 월별 학교·업장 실적에 금액의 출처와 미확인 수치를 표시한다. POS·실송금 연동 완료로 표현하지 않는다.
- 완료 기준: 일반 운영자가 금융 처리 버튼이나 직접 API로 권한을 우회하지 못하고, 중복 처리·실패·불일치가 확인 가능하다.

## 6. 권한·감사와 공통 계약

### ADM-09: 운영 일정·콘텐츠 관리

- [ ] 학교별 오늘밤 회차·기획 행사·모임 일정을 구분해 조회하고, 기존 편성 기능과 연결한다. 새로운 매칭 엔진으로 교체하지 않는다.
- [ ] 운영자가 지정하는 행사 제목·사진·장소·일시·모집 기간·인원 조건의 누락을 확인하고 미리보기 후 공개한다.
- [ ] 편성되지 않은 날짜를 확정 행사처럼 표시하거나 예시 인원으로 채우지 않는다. 접수 중지·행사 취소 시 영향받는 참가자와 알림 상태를 확인한다.
- 완료 기준: 공개 전후의 사용자 표시와 참가 상태가 일치하며, 일정 변경이 기존 참가자의 동의·예약 조건을 임의 덮어쓰지 않는다. 새 편성 기능과 운영 데이터 생성은 별도 구현·적용 범위를 확인한다.

### 역할별 권한과 공통 기록

- 권장 역할 분리: 최고관리자 / 담당 학교 운영자 / 업주 / 직원 / 금융 처리 담당자. 현재 모든 세부 권한이 구현됐다는 뜻은 아니다.
- [ ] 민감 정보 열람, 권한 부여·회수, 예약 취소, 금융 변경에 행위자·대상·시각·사유·변경 전후를 남긴다.
- [ ] 프론트엔드에서 버튼을 숨기는 것과 서버 권한 검사를 함께 구현한다. 요청한 학교·업장·예약의 실제 소유 범위를 확인한다.
- [ ] 브랜치별로 새 인증·DB·예약 원장을 만들지 않는다. 공용 계약은 [인터페이스 계약](../../engineering/INTERFACE_CONTRACT.md)에 따라 담당자를 정해 합의한다.
- [ ] 서버가 확정한 예약 ID·조건 버전·동의 인원·상태를 사용한다. 사용자 앱과 업장 앱이 각각 인원을 계산해 서로 다른 확정값을 만들지 않는다.
- 완료 기준: 최소 두 학교·두 업장·서로 다른 역할 계정으로 허용·차단 시험을 하고, 권한 회수와 동시 처리까지 검증한다.

## 8. 권장 구현 순서와 인수 기준

1. **학교·권한 경계**: 학교 전환, 담당 범위, 연락처·금융 권한과 회수 차단 시험.
2. **업장 온보딩**: 등록·중복 점검·초대·승인·프로필 검토·사용자 노출, 회차 없는 상태 시험.
3. **공통 예약 연결**: 동의한 사용자 → 정확한 업장 담당 → 동일 조건 수락/거절 → 동일 예약 결과 확인.
4. **운영 예외**: 날짜별 참가자, 연락·참석 미확인, 신고·정정·이의, 담당자 부재 대응.
5. **감사·알림·금융 검증**: 중복 처리·권한 회수·발송 실패·금전 기록 불일치 검사.
6. **운영 효율 개선**: 좌석·시간표, 확인 근거가 있는 월별 실적, 반복 업무 자동화.

각 단계 보고에는 변경 파일·사용자 흐름 캡처·권한별 시험·실패 시 복구·남은 미검증 항목을 함께 적는다. 정적 시안·HTTP 성공·로컬 테스트만으로 운영 완료라고 보고하지 않는다.
착수 전 담당자와 공용 변경 범위를 합의한다. 문서 전달은 작업 결과가 아니라 업무 기준 전달이며, 실제 일정·완료 여부는 담당자의 응답과 검증 증거로 갱신한다.
