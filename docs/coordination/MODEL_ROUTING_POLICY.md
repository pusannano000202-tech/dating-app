# Quantum 동적 모델 라우팅 정책

최신 기준: 2026-08-30
적용 저장소: `C:\데이팅앱만들기`

## 1. 목적과 불변 경계

팀은 업무 영역과 파일 소유권을 정하고, 모델은 각 단계의 판단 난이도·영향 범위·위험으로 선택한다. 모델을 팀에 고정하거나 사용 비율을 목표로 삼지 않는다.

- 구현자와 독립 검증자는 분리한다.
- `git add`·commit·push, 원격 DB/Auth/Storage/RLS/RPC·migration 적용, 실제 결제, production 배포·제출의 승인은 서로 분리하며 최종 승인은 사용자에게만 있다.
- 결제·환불·인증·DB/RLS·개인정보·공용 계약·production은 fast lane으로 내리지 않는다.
- 열린 제품·디자인 판단과 고위험 설계는 충분한 Sol 검토를 유지한다. 단순 확인에 Sol을 기계적으로 쓰지 않는다.

## 2. 모델 역할

| 모델 ID | 적합한 역할 | 단독으로 맡기지 않을 일 |
|---|---|---|
| `gpt-5.3-codex-spark` | 잠긴 명세의 짧고 기계적으로 대조 가능한 구현·변환 | 열린 방향, 고위험 설계, 최종 승인 |
| `gpt-5.6-luna` | 결정론적 사실 확인, 반복 검사, 로그·자료 정리 | 제품 방향, 정책 확정, 고위험 설계 |
| `gpt-5.6-terra` | 범위가 잠긴 일반 분석·구현·원인 진단 | 열린 제품 방향 확정, RED 최종 검토 |
| `gpt-5.6-sol` | 모호한 문제 정의, 전체 제품 판단, 브랜드, 고위험 설계·독립 검토 | 정해진 단순 반복의 대량 수행 |

Spark는 **가용하고**, 요구·허용 파일·출력·검증·종료 조건이 모두 잠긴 GREEN 작업일 때 후보가 된다. 지원되지 않거나 잠금 조건이 하나라도 없으면 강제하지 말고 Luna 또는 Terra를 작업에 맞게 고른다. Spark 결과는 스스로 승인하지 않으며, 한 번 실패·범위 확대·요구 충돌·원인 불명이면 Terra로, RED 신호면 Sol로 올린다.

## 3. 두 실행 레인

### Fast lane

아래 중 하나이고 RED 경계가 없는 내부 하위 작업에 사용한다.

- 읽기 전용 사실 확인: 파일 존재, 값·로그·테스트 결과 수집, 화면의 표시·클릭 여부처럼 판단을 만들지 않는 확인
- 잠긴 단순 수정: 위치·문구·수치·정확한 파일과 기대 diff가 지정되고, 테스트 또는 비교 기준이 있는 수정
- 부모가 이미 범위와 종료 조건을 잠근 내부 하위 작업

기본 선택은 Luna `low`~`medium`(관찰), Spark `medium`~`high`(가용한 잠긴 단순 구현), Terra `medium`(짧은 잠긴 해석/수정)이다. Fast lane은 짧은 ownership·금지·합격 기준만 전달하며, 대표실 보고·승인 Gate·전체 작업 카드·정책 재독을 요구하지 않는다. 사용자 승인 자체가 필요한 외부 변경은 fast lane이 아니다.

### Full lane

아래 중 하나면 full lane으로 전환한다.

- 열린 제품/프론트 디자인, 핵심 사용자 흐름, 브랜드·정보 구조 판단
- 결제·환불·인증·DB/RLS·개인정보·공용 계약·migration·`lib/types.ts`·`lib/supabase.ts`
- production, release candidate, `main`, Vercel 배포 판단 또는 실제 서비스 영향
- 여러 팀/레이어/공용 파일이 얽힘, 증거 충돌, rollback 부재, 같은 원인 불명 실패 2회

열린 프론트 디자인의 첫 해석·첫 보고·전체 설계와 최종 제품 품질은 Sol `xhigh`다. 브라우저의 표시·잘림·겹침·CTA·URL 같은 사실은 Luna `low`~`medium`, 일반 원인 분석과 잠긴 구현은 Terra `medium`~`high`가 맡을 수 있다. RED 설계·최종 검토는 Sol `xhigh`~`max`로 올린다.

## 4. 부모 해석 재사용 계약

같은 논리 작업 트리에서는 부모가 한 번 정책을 해석하고, 각 자식에게 아래 `resolved routing`을 전달한다. 유효한 계약을 받은 자식은 정책 파일과 대표실 스킬을 다시 읽지 않는다.

```text
routing_version: 2026-08-30
root_task: 부모 작업 ID와 결과
lane: fast | full
stage / risk:
model_id / reasoning_effort:
why_this_route:
allowed_files:
forbidden_actions:
acceptance_criteria:
evidence_return: 결과를 누구에게 어떤 압축 증거로 돌려줄지
escalate_when:
approval_basis: 해당 시 정확한 사용자 승인 문장 또는 "없음"
```

- 계약은 같은 요청의 하위 트리에만 유효하다. 요청·명세·파일 소유권·Gate가 바뀌면 부모가 다시 해석한다.
- 자식은 계약의 파일·금지·합격 기준을 확인하고 작업한다. 모순, RED 신호, 범위 확대, 실패 조건을 만나면 멈추고 부모에게 올린다.
- 부모는 결과를 회수해 독립 검증과 승인 필요 여부를 판단한다. 자식이 자기 결과를 최종 승인하거나 다른 작업방을 열지 않는다.
- full lane의 별도 작업방, 승인 Gate, 대표실 회수에만 `quantum-executive-reporting`을 추가 적용한다.

## 5. 사고 강도와 Ultra

| 강도 | 사용 기준 |
|---|---|
| `low` | 하나의 기준을 그대로 확인 |
| `medium` | 조건은 여럿이지만 정답·종료가 명확 |
| `high` | 여러 상태·파일·예외·원인 후보 추적 |
| `xhigh` | 제품 전체 방향, 복합 설계, 고위험 검토 |
| `max` | 동시성, rollback, 충돌 요구, 반복 실패 해결 |
| `ultra` | 독립 축이 매우 많은 대형 문제의 자동 분업 |

Ultra는 기본값이 아니다. 다음을 모두 만족하고 **사용자의 명시적 승인 근거(승인 문장, 시각, 대상 범위)**를 작업 카드에 기록할 때만 쓴다: 독립 조사·검증 축 4개 이상, 사전 정확 분해가 어려운 대형·모호 문제, 병렬화의 실질적 이점, 파일 충돌이 없는 읽기/분리 작업, 예상 하위 작업 수·추가 비용·종료 조건의 사전 보고. `알아서`, 일반적인 진행 허가, 모델 선택 위임은 Ultra 승인 근거가 아니다.

## 6. 검증과 보고 경계

- Luna는 화면 사실·테스트 결과를 보고하되 `좋은 디자인`·`출시 가능`을 확정하지 않는다.
- Sol은 제품 적합성·브랜드·고위험 결정을 검토하되, 반복 실행을 직접 독점하지 않는다.
- Terra는 잠긴 일반 구현을 담당할 수 있지만 RLS·migration 순서·결제 정합성·rollback의 최종 판단은 Sol 검토를 거친다.
- fast lane 내부 결과는 부모에게 재현 절차, 핵심 diff/캡처, 테스트 결과, 미확인만 짧게 반환한다.
- full lane의 별도 작업방은 승인 Gate와 대표실 회수 형식을 사용한다.

## 7. 최소 배정 기록

Fast lane은 아래 다섯 항목이면 충분하다.

```text
작업 / 소유(허용 파일):
금지:
모델·강도와 이유:
합격 기준:
부모 반환 증거·승격 조건:
```

Full lane은 여기에 단계, 위험(GREEN/YELLOW/RED), 승인 근거, 중단 조건, 독립 검증자와 결과 반환 대상을 더한다. 모델은 정확한 ID와 영문 사고 강도로 적고, 지원되지 않는 조합을 임의 대체하지 않는다.

## 8. 운영 보정

2주 단위로 정책 read 횟수, 대표실 보고 사용처, 모델·강도, 재작업, 결함, 사용자 판정 번복을 함께 본다. 목표는 특정 모델 사용량이 아니라 불필요한 재독·보고를 줄이면서 RED 경계와 독립 검증을 보존하는 것이다.
