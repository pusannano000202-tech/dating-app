# Quantum 모바일 마이 허브 설계

- 작성일: 2026-08-09
- 선택안: A, 행동별로 묶은 마이
- 상태: 화면 구조 사용자 승인, 구현 전 서면 검토 대기
- 대상: `apps/mobile`

## 1. 목적

현재 마이 화면은 프로필, 친구, 알림, 보증금, 안전, 설정이 한 목록에 섞여 있다. 로그아웃 버튼도 화면 상단의 주 행동처럼 보여 사용자가 다음에 무엇을 해야 하는지 알기 어렵다.

마이 화면을 다음 네 가지 목적에 맞춰 다시 구성한다.

1. 미완료된 프로필 행동을 한 번에 이어서 할 수 있어야 한다.
2. 친구 요청, 친구 관리, 약속 제안을 빠르게 찾을 수 있어야 한다.
3. 만남 사진과 지난 만남을 확인할 자리를 마련해야 한다.
4. 보증금, 다시 만나지 않기, 신고와 계정 설정을 안전하게 분리해야 한다.

## 2. 사용자 경험 원칙

- 화면 상단의 주 행동은 한 개만 강조한다.
- 실제 데이터가 없는 숫자나 활동 알림은 만들지 않는다.
- 연결되지 않은 기능을 눌렀을 때 성공한 것처럼 보이지 않는다.
- 채팅은 하단 탭으로 만들지 않고 확정된 만남 또는 친구 상세에서만 진입한다.
- 설정과 로그아웃은 화면 하단의 계정 영역으로 이동한다.
- 성향 설문은 마이의 주요 메뉴에서 제거한다.
- 성향 설문의 기존 저장값, API, 가입 완료 판정은 별도 계약 변경 전까지 유지한다.

## 3. 화면 정보 구조

### 3.1 상단 계정 영역

- 제목: `마이`
- 설명: `내 정보와 만남을 한곳에서 관리해요.`
- 표시 정보: 닉네임, 학교, 프로필 완료율
- 주 행동: 서버가 알려주는 다음 미완료 프로필 단계
- 모든 프로필 단계가 끝났으면 주 행동 대신 `프로필 보기`를 표시한다.

프로필 완료율과 다음 행동은 클라이언트가 임의로 계산하지 않고 온보딩 API 결과를 사용한다.

### 3.2 사람

상단 빠른 진입은 세 개로 제한한다.

- 친구
- 받은 요청
- 알림

숫자는 실제 API 응답이 있을 때만 표시한다. 실패하거나 불러오는 중이면 숫자를 숨기고 해당 상태를 화면에 알린다.

`친구 관리`를 별도 중복 메뉴로 만들지 않는다. 친구 목록 화면 안에서 다음 기능을 탭으로 분리한다.

- 내 친구
- 받은 요청
- 보낸 요청
- 같은 학과 추천
- 그룹 초대

친구 상세에서는 밥, 카페, 산책, 직접 입력 약속을 제안할 수 있다. 일반 채팅은 확정된 관계 또는 만남 계약이 있을 때만 노출한다.

### 3.3 내 프로필

- 기본정보
- 프로필 사진
- 이상형 월드컵

성향 설문은 이 목록에서 제거한다. 하지만 현재 가입 완료와 매칭 진입이 Big5 값을 요구하므로 이번 마이 화면 구현만으로 설문 API, 저장값, 라우팅 계약을 삭제하지 않는다. 설문 자체를 폐기하려면 매칭 입력 계약과 온보딩 완료 판정을 함께 바꾸는 별도 작업이 필요하다.

### 3.4 만남과 기록

- 친구와 약속
- 우리 사진첩
- 지난 만남

`친구와 약속`은 기존 친구 상세의 약속 제안 기능으로 연결한다.

`우리 사진첩`은 만남 인증을 위해 업로드한 사진을 같은 만남 참가자끼리 보는 전용 공간이다. 구현 전에는 실제 메뉴처럼 노출하지 않는다. 구현 후에는 다음 조건을 만족해야 한다.

- 동일 `event_id` 참가자만 조회 가능
- 환불 증거 원본과 사용자 앨범 표시 자산의 보존 목적 분리
- 인증사진 제출 성공 후 앨범 항목 자동 생성
- 만남별 묶음과 날짜 표시
- 다른 이벤트 참가자는 접근 불가

### 3.5 결제와 안전

- 보증금
- 다시 만나지 않기
- 신고와 안전 도움
- 설정과 로그아웃

보증금 화면은 잔액, 반환, 다음 매칭 이월, 별도 후원을 구분한다. 아직 서버 계약이 없는 행동은 활성화하지 않는다.

`다시 만나지 않기`는 친구 삭제나 만남 이후 제외한 사람을 관리한다. 제외하면 서로의 프로필이 보이지 않고 다음 매칭 후보에서 제외된다. 사용자가 직접 해제할 수 있다.

신고는 보증금 자동 몰수와 동일한 행동으로 취급하지 않는다. 신고 접수, 증거 상태, 운영 정책 결과를 분리한다.

## 4. 기능 상태 표시 규칙

제품 화면에는 개발 상태 배지를 노출하지 않는다. 설계와 QA에서만 다음 상태를 사용한다.

- `연결됨`: 모바일 화면, API, 원격 DB가 실제 연결되고 검증됨
- `부분 연결`: 화면과 일부 API가 있지만 전체 사용자 흐름이 끝나지 않음
- `미구현`: 화면 또는 서버 계약이 없음

미구현 메뉴는 운영 화면에서 숨긴다. 독립적인 빈 상태까지 구현된 뒤에만 메뉴를 공개한다.

## 5. 데이터 흐름

### 5.1 화면 시작

1. 모바일 세션을 확인한다.
2. 온보딩 상태, 친구 현황, 읽지 않은 알림 수, 보증금 요약을 서로 독립적으로 요청한다.
3. 한 요청이 실패해도 전체 마이 화면을 막지 않는다.
4. 각 영역에서 로딩, 성공, 실패 상태를 따로 표시한다.

### 5.2 주 행동 결정

온보딩 API의 `next_step`을 다음 순서로 연결한다.

- `basic`: 기본정보 이어하기
- `worldcup`: 이상형 월드컵 이어하기
- `survey`: 현재 계약상 성향 설문 이어하기
- `photos`: 프로필 사진 등록하기
- `complete`: 프로필 보기

마이 목록에서는 성향 설문을 숨기더라도 기존 계정이 `survey` 단계에 있으면 상단 주 행동에서는 설문 완료를 안내한다. 설문 폐기 계약이 적용되면 이 분기와 서버 완료 판정을 함께 제거한다.

## 6. 상태와 오류 처리

- 세션이 없으면 로그인 화면으로 이동한다.
- 프로필 요약 실패 시 계정 이메일을 대신 노출하지 않고 `프로필을 불러오지 못했어요`와 재시도를 표시한다.
- 친구 또는 알림 수를 불러오지 못하면 `0`으로 속이지 않는다.
- 보증금 API 실패 시 반환 또는 이월 버튼을 비활성화한다.
- 네트워크 재시도 중 같은 요청이 중복 실행되지 않게 한다.
- 로그아웃은 설정 화면에서 한 번 더 확인한 뒤 실행한다.

## 7. 시각 및 접근성 계약

- 390x844를 기준으로 가로 넘침이 없어야 한다.
- 데스크톱 모바일 웹 미리보기에서도 최대 폭 430px을 유지한다.
- 카드 반경은 최대 8px, 터치 영역은 최소 44px로 한다.
- 제목은 24px 내외, 섹션 제목은 17px 내외로 제한한다.
- 색만으로 상태를 구분하지 않고 문구와 아이콘을 함께 사용한다.
- 포커스 표시, 스크린리더 이름, 로딩과 오류 알림을 제공한다.
- 한 화면의 강조색은 학교 파랑, 행동 코랄, 안전 청록으로 역할을 분리한다.

### 7.1 사진과 상태 표시 원칙

- 상단 프로필은 현재 사용자가 소유한 대표사진의 짧은 유효기간 서명 URL을 사용한다. 사진이 없으면 임의 인물 사진 대신 이니셜을 표시한다.
- 사람 영역에는 서버가 수락된 친구로 확인한 사용자만 노출한다. 친구 사진도 짧은 유효기간 서명 URL만 사용하고, URL을 만들지 못하면 이니셜로 대체한다.
- 만남 사진은 현재 사용자가 실제로 참가한 `event_id`의 앨범만 사용한다. 디자인 예시 이미지를 실제 만남 기록처럼 표시하지 않는다.
- 보증금은 실제 10,000원 계약과 서버 상태를 사용한다. 현재 활성 보증금 범위를 알 수 없으면 `납부 완료`로 추정하지 않고 `보증금 확인` 행동만 보여준다.
- 신고와 안전 영역은 사진 대신 방패 아이콘, 문구, 상태색으로 표현한다. 연결되지 않은 신고·제외 기능은 운영 화면에서 숨긴다.
- 모든 사진은 안정된 종횡비와 `cover` 방식으로 자른다. 사진 로딩이 카드 높이와 주변 버튼 위치를 바꾸지 않아야 한다.

## 8. 구현 단계

### 1단계: 마이 허브 재구성

- 현재 연결된 프로필, 친구, 알림, 보증금 메뉴를 행동별로 재배치
- 실제 온보딩 상태에 따른 상단 주 행동
- 로그아웃을 설정 하위로 이동
- 성향 설문을 마이 목록에서 제거
- 모바일 390x844와 웹 미리보기 검증

### 2단계: 친구와 안전 관리

- 친구 화면 내부 탭 구조
- 받은 요청과 알림 실제 개수 연결
- 다시 만나지 않기 목록과 해제 흐름
- 친구 상세의 약속 제안과 확정 상태 정리

### 3단계: 만남 기록

- 만남 인증사진의 앨범 자동 저장
- 만남별 앨범과 참가자 접근 제어
- 지난 만남과 확정 채팅 진입
- 보증금 증거와 앨범 표시 자산의 분리 보존

### 4단계: 결제 완성

- 보증금 전액 반환
- 다음 매칭 이월
- 별도 후원
- 결제 실패, 중복 요청, 취소와 정산 상태 검증

## 9. 검증 기준

- 로그인 후 마이 진입과 새로고침이 정상이어야 한다.
- 프로필 미완료 단계별 주 행동이 정확한 화면으로 이동해야 한다.
- 완료 계정이 다시 가입 단계로 강제 이동하지 않아야 한다.
- 친구, 요청, 알림 수가 실제 응답과 일치해야 한다.
- 없는 기능이 성공한 것처럼 표시되지 않아야 한다.
- 로그아웃 후 보호 화면에 다시 접근할 수 없어야 한다.
- 모바일 390x844와 430x932에서 가로 넘침, 겹침, 잘린 텍스트가 없어야 한다.
- 실제 계정 두 개로 친구 요청, 수락, 약속 제안, 알림을 확인해야 한다.
- 앨범과 다시 만나지 않기는 원격 Supabase RLS 검증 전 완료로 판정하지 않는다.

## 10. 비범위

이번 설계만으로 다음을 완료라고 보지 않는다.

- 성향 설문 데이터와 매칭 가중치의 완전 폐기
- 일반 사용자끼리의 무제한 채팅
- 보증금 반환과 후원의 실제 결제 처리
- 만남 사진 앨범의 원격 DB와 Storage 정책
- Google Play 출시와 실기기 푸시 알림
- production 배포
