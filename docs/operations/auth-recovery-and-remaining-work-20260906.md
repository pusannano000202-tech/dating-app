# 인증 복구 상태와 전체 기능 잔여 작업 — 2026-09-06

## 판정

**로컬 로그인 장애를 해결했다.** 새 테스트 계정으로 실제 Auth OTP 확인→최소 가입 저장→새로고침 후 저장 정보 유지→커뮤니티·홈 접근까지 확인했다. 그러나 **전체 서비스 완료나 운영 출시 완료는 아니다.** 아래는 승인된 전체 기능을 끝내기 위한 잔여 작업표이며, 일부 기능만 골라 완료 처리하지 않는다.

## 오류가 생긴 이유와 수정 범위

1. 직전 방문 맛집 UI 검수를 위해 실행한 서버가 `--offline-ui` 모드였다. 이 모드가 인증 설정을 비우는데 사용자는 홈/로그인까지 되는 실행으로 받아들일 수 있었다. 실행 모드·진입 주소·캐시를 분리하고 공개 검수 안내에서는 무한 재시도 버튼을 제거했다.
2. Docker는 오래된 임시 통신 소켓을 제거하지 못해 종료됐다. `Docker/run` 및 `docker-secrets-engine` 임시 폴더를 이름 변경으로 보관하고 재생성했다. 공장 초기화나 DB 볼륨 삭제는 하지 않았다. 기존 다른 로컬 스택은 보존했다.
3. Supabase CLI 2.116.0은 SMS 제공자가 모두 꺼져 있으면 `enable_signup=true`와 test OTP 설정이 있어도 전화 로그인을 끈다. 더미 자격증명과 지정 테스트 번호만 사용하는 로컬 구성으로 바꾸고, 앱은 네 번호 외 OTP 시작 요청을 사용자 조회/DB challenge/provider 호출 전에 차단한다. 런처는 정확한 테스트 매핑·더미값·전화 활성 여부·자동 인증 비활성을 확인한다. 테스트 번호는 GoTrue의 실제 OTP/세션 처리를 거치며 SMS 전송은 생략된다. [공식 Auth 전화 처리 코드](https://github.com/supabase/auth/blob/master/internal/api/phone.go), [공식 CLI 설정](https://supabase.com/docs/guides/local-development/cli/config)
4. 실제 Auth는 전화번호를 `8210…` 형식으로 저장하는데 최소 가입 DB 함수 네 개가 `+8210…`만 허용했다. 브라우저에서 올바른 코드로 Auth 확인은 성공했지만 앱 완료 RPC가 `verified_phone_missing`으로 실패하는 것까지 재현했다. `20260906081607_accept_gotrue_phone_storage.sql`을 전용 로컬 DB에만 추가 적용해 두 형식을 엄격하게 인정하고, 공개 앱 전화번호를 `+8210…`으로 정규화했다. 원본 migration·Auth 사용자 저장값은 변조하지 않았다. 인증·권한·만료 검사와 함수 권한을 보존한 것을 독립 검토했다.

로컬 도구에서 관찰한 공급자 코드 수명은 6000초이며 앱 challenge는 기존 상한 3600초 이내에 먼저 만료한다. 운영 전역 상한을 늘리거나 미인증 상태를 승인 상태로 바꾸지 않는다.

## 통합 local UAT 순서

1. 확인한 local 신규 로그인 정상/틀린 코드 경로를 기반으로 만료·재전송·로그아웃 후 재로그인 실패 경계를 확장 검증한다.
2. 기존 이메일/OAuth 계정 연동 보존과 최소 가입/매칭 추가 자격 경계를 다계정으로 확인한다.
3. MBTI 저장·수정·삭제·철회와 통계 표본 부족을 둘 이상의 계정에서 확인한다.
4. 오늘/이번 주 각각의 신청·마감·취소·배정을 실제 DB에서 확인한다.
5. 보드/비보드 원천 네 조합의 계속 만나기, 동의, 출석, Day/실제 번호, 정정 복구를 확인한다.
6. 같은 대상 round를 사용자→업장→운영자→최고관리자 순서로 대조한다.
7. 로컬 가짜 금액만으로 결제 상태/만료/retry/worker를 확인하고, Toss/실결제는 별도 승인 뒤 분리 실행한다.
8. 서버/DB 재시작 후 가입·신청·동의·대진·권한 상태가 유지되는지 확인한다.

## 운영·원격 완료에 필요한 별도 증거

- 원격 Supabase migration 적용, RLS/RPC, 실제 계정 동시성 및 백업/철회 보존 확인
- SMS provider 계약과 실발송, Toss sandbox 및 실결제/실환불, Push 실제 기기, cron 설치/실행
- Vercel/EAS 환경 변수·feature flag 조합과 배포 후 smoke test
- 사진/배달 후보/장소의 사용권·영업 정보·외부 링크 최신성
- 실제 대상자 5명 중 4명 이상 무도움 핵심 동선 완료 및 첫 행동 10초 이해 관찰

위 항목은 로컬 화면, fixture, HTTP 200, 자동 테스트, 정적 SQL 검사와 서로 대체되지 않는다. 각 항목이 해당 환경의 증거로 닫혀야 전체 기능 완료로 판정할 수 있다.

## 이번 검증에서 추가로 남긴 경계

- 실제 Auth가 성공한 뒤 앱 completion RPC가 실패하면 공급자 OTP/세션과 앱 challenge가 부분 성공 상태가 될 수 있다. 현재 원인이었던 번호 형식은 고쳤지만, 운영용 멱등 재시도·보상 설계와 장애 주입 테스트는 별도 필요하다.
- 가입 완료 화면에서 새로고침하면 저장값은 보존되지만 기본정보 화면의 1/6 단계로 다시 보인다. 데이터 유실은 아니며, 재방문 완료 상태를 더 명확히 표시할 UI 보완 후보다.
- 외부 OAuth/이메일 OTP는 이번 브라우저 완주 대상이 아니다. 로컬 이메일 코드 템플릿과 OAuth 제공자별 설정/복귀는 별도 확인한다.
- 앱 밖에서 loopback Auth API를 직접 호출하는 경우까지 네트워크 수준의 외부 요청 차단을 보장하지는 않는다. 더미 자격증명에는 실제 발송 권한이 없으며, 더 강한 로컬 격리가 필요하면 테스트 전용 SMS hook을 추가 검토한다.
