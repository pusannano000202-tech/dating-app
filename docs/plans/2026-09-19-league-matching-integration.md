## 3. 목표 A — 리그를 내 상태에 맞는 화면으로 바꾸기

### A1. 둘러보기와 내 팀 분리

- 공통 탐색 탭: `학과 순위 / 모집 팀 / 합류 대기판`.
- 소속 팀이 있으면 리그 첫 진입에서 `내 팀` 요약과 다음 행동을 바로 표시한다. 강제 이동시켜 순위 탐색을 막지는 않는다.
- 팀 없는 사용자에게만 새 팀 만들기·대기 등록을 안내한다. 이미 팀원인 사용자에게 신규 참가 안내를 반복하지 않는다.
- 순위의 1~3위 강조·학과 상징·실제 기록을 보존한다. 실제 기록이 없으면 우승 학과를 꾸며내지 않는다.
- 등록 인원·팀 수는 조회 범위와 일치시킨다. 실패는 0명으로 표시하지 않는다.

### A2. 팀 없음: 세 가지 선택을 분명하게

1. `모집 팀` → 팀 정보와 자리 지도 → 빈자리 → 자기소개·장점 및 해당 보증금 확인 → 신청 상태.
2. `합류 대기판` → 가능한 포지션 복수 선택 → 해당 보증금 확인 → 등록 상태·받은 초대.
3. `새 팀 만들기` → 팀명·종목별 지도·내 자리·티어 → 생성 확인 → 새 팀 상세.

팀 만들기는 빈 폼을 여는 동작과 실제 저장을 구분한다. 뒤로 가기만으로 방을 생성하지 않는다. 보증금 조회·납부·신청 접수는 별개 상태로 표시한다.

### A3. 팀 있음: 모집에서 대결까지

- 모집 중: 팀명·확정 인원·검토할 신청을 우선 표시. `포지션 / 신청 / 우리 팀 채팅`으로 나눈다.
- 빈자리 지도 선택 → 기존 친구 초대. `팀원 찾기` → 대기판 후보. 학과 모집 소식 공유는 보조 행동으로 둔다.
- 신청 한마디·장점은 권한 있는 주장만 읽는다. 기존 방 공지·개인 알림·채팅 탭의 연결을 보존한다.
- 정원과 참가 조건이 충족되면 `대결 상대 찾기`를 주 행동으로 바꾼다. 덜 모였을 때도 상대 둘러보기는 가능하되 제안 가능 조건을 명시한다.
- 상대 상세: 팀 합계 점수와 각 포지션 티어·명단, 받은/보낸 제안 상태. 표시는 가능하되 제안·수락은 현재 주장 권한을 서버에서 검사한다.
- 상대 수락 → 양 팀 경기 채팅 → 일정 제안·상호 확정 → 출석·결과·분쟁 처리. ‘우리 팀 채팅’과 ‘경기 채팅’은 소속을 구분하고 모두 채팅 탭에 남긴다.
- 주장 위임·팀 탈퇴·팀 관리 메뉴는 내 팀의 더보기로 옮긴다. 신청·경기·보증금 제한을 UI 이동 때문에 완화하지 않는다.
- 축구에도 같은 구조를 적용하되 기존 전술·포지션 지도를 보존한다. LoL 티어를 축구에 억지로 붙이지 않는다.

### A4. 상태와 복구

- 화면 단계·팀 ID를 URL에 표현해 새로고침, 뒤로/앞으로, 알림 링크로 같은 상태에 복귀한다. 기존 `sport`, `category`, `challenge`, `panel` 링크를 깨지 않게 호환한다.
- 서로 다른 팀을 보는 중 내 팀 데이터가 섞이지 않도록 탐색 대상과 소속 팀 상태를 분리한다.
- 중복 승인·정원 초과·마감 직전 신청·탈퇴·취소·권한 변경 때 최신 상태를 다시 읽고 다음 행동을 설명한다.
- 팀 합류 확정 시 대기 글과 다른 초대를 종료하는 기존 서버 동작을 검증한다. 나와 다른 주장에게 각각 종료 이유·다음 행동을 알려준다.
- 대기 중단은 자동 환불 완료가 아니다. 반환 요청과 처리 상태를 별도로 안내한다.

## 4. 목표 B — 기존 매칭을 끊김 없이 연결하기

### B1. 먼저 연결 상태를 분리 진단

실행 작업공간·앱 포트·연결 DB·인증 callback을 확인한 뒤, UI → 인증 → 회차 조회 → 신청 gate → 결제 상태 → 배정 → 만남 진행으로 추적한다.

- 과거 검수 모드를 켜거나 인증을 우회해 페이지가 보이기만 하는 수정을 하지 않는다.
- 오늘 모집 없음 / 아직 오픈 전 / 마감 / 내 신청 진행 중 / 서비스 오류를 별개 상태로 만든다.
- 모집 회차가 없을 때도 이미 접수된 신청·결제·진행 중인 만남을 숨기지 않는다.
- 기존 로컬 DB를 초기화하거나 다른 오래된 DB로 바꿔 완료처럼 보이지 않는다.

### B2. 오늘밤의 기존 흐름 보존

`오늘의 3개 콘텐츠 보기 → 선호 1·2·3순위·참가 조건 확인 → 신청 → 배정 대기 → 기존 수락·보증금 절차 → 만남 준비 → 허용된 시점의 채팅·출석 → 활동 안내 → 종료 후 선택`

- 하나의 모집 풀을 유지한다. 활동별로 사람을 갈라 모집하거나 배정 뒤 새 투표를 만들지 않는다.
- 팀 구성과 팀 단위 활동 선호 합산·장소 수용량 처리를 기존 엔진과 대조한다.
- 기존 사진 분석·프로필·선호·연애 상태 입력이 실제 배정까지 전달되는지 추적한다. 개인 외모 원점수는 화면/API/로그에 공개하지 않는다.
- 현재 코드 기본 시각은 신청 마감 18:30, 배정 발표 18:32, 보증금 기한 18:45, 파트너 수락 18:50, 공개 18:55, 도착 19:20, 시작 19:30(KST)이다. 이는 코드 관찰이며 새 운영 정책 승인이 아니다. 확정된 최신 정책과 대조하고 임의 변경하지 않는다.
- 리그의 ‘합류 즉시 팀 채팅’ 규칙을 매칭에 적용하지 않는다. 매칭의 시간·참가 상태·동의 조건을 서버 및 실제 화면에서 검증한다.
- 순위 선택, 단계 이동, 갱신 실패, 앱 복귀 때 선택·진행 상태를 잃지 않게 한다.

### B3. 자동 회차 생성과 실제 신청 연결

- 기존 prepare·배정·통지·정산 작업의 인증, 실행 조건, 한국 날짜, 중복 실행, 놓친 실행 복구를 검사한다.
- 실제 장소·수용 인원·모집 gate가 준비됐을 때만 모집 가능으로 표시한다. 단순히 env를 모두 true로 바꾸지 않는다.
- 테스트용 격리 저장소에서 오늘 회차·3개 콘텐츠·신청·배정·불성사·미납·취소 시나리오를 검증한다.
- 사용 중 로컬 DB에 새 데이터를 넣거나 SQL을 적용하는 단계는 대상과 변경을 먼저 제시하고 별도 승인 후 실행한다. 미승인이어도 읽기·코드 수정·격리 테스트는 진행 가능하다.

### B4. 이벤트 캘린더·커플·5회 만남

- 운영자가 공개한 날짜·콘텐츠·장소 → 행사 상세 → 조건·보증금 확인 → 신청 상태로 이어진다.
- 미적용 SQL 4개는 실제 카탈로그와 비교한 뒤 필요한 것만 순서대로 검증한다. 일괄 적용하지 않는다.
- 연애 중이면 날짜가 정해진 커플 행사로 안내하고 파트너의 직접 수락·각자 자격·납부 상태를 확인한다. 싱글 모집에 섞지 않는다.
- 참가 인원은 실제 서버 집계와 갱신 시각으로 표시한다. 일시 조회 실패를 0명이나 마감으로 표현하지 않는다.
- 만화 안내는 기존 캐릭터·말풍선 구성과 진행 데이터에 연결한다. 정해진 시간·출석 조건 전에는 실제 활동 진행처럼 노출하지 않는다.
- 5회 만남은 첫 만남 이후 당사자가 선택하는 기존 후속 흐름이다. ‘오후 만남’이나 별도 세 번째 모집 입구로 만들지 않는다. 미확정 회차 콘텐츠를 승인된 프로그램처럼 추가하지 않는다.

## 5. 공통 보존·보안 기준

- 이번 디자인은 보증금 금액·납부 시점·환불 정책 변경 승인이 아니다. 각 활동의 서버 정책·원장을 기준으로 하고 일반 모임 규칙을 오늘밤에 복사하지 않는다.
- 기존 납부가 있다고 무조건 면제하지 않는다. 소유자·원거래·활동 배정·잔액 잠금·반환 진행 상태를 확인하고, 허용된 이월만 명시 동의로 수행한다.
- 동일 금액을 여러 활동에 중복 배정하거나 환불과 이월을 동시에 처리할 수 없어야 한다.
- 반환은 사용자 신청으로 시작하고 공급자 확인 전 완료 표시를 하지 않는다. 현재 합의된 원결제 취소 방식을 유지한다.
- 사진·연락처·소개·점수는 기존 개인정보 접근권한을 보존한다. 알림 잠금화면에는 민감 내용을 넣지 않는다.
- 홈·마이·모임·커뮤니티·기존 대화·학과 순위를 제거하지 않는다. 하단 탭 소속은 리그=모임, 대화=채팅, 자동 매칭=매칭으로 유지한다.
- 승인 이미지의 인원·팀명·아바타·티어 그림은 예시다. 구현에는 기존 자산과 실제 조회 데이터를 사용하며 예시를 실제 데이터로 저장하지 않는다.

## 7. 완료 기준과 검증

### 리그 필수 시나리오

- 팀 없는 사람: 팀 찾기/대기 등록/생성이 명확히 구분되고 각각 올바른 다음 화면으로 간다.
- 주장: 신청 도착을 내 팀·전역 알림·채팅 공지에서 확인하고 승인 후 확정 인원이 갱신된다.
- 일반 팀원: 팀 대화·명단·상대 전력은 보되 주장 권한 작업은 서버에서도 거부된다.
- 초대 여러 건: 한 팀 합류 확정 후 대기 종료·다른 초대 종료·양쪽 알림이 일치한다.
- 완성 팀: 직접 상대 제안→상대 수락→경기 채팅·일정 확정. 불성사/거절/취소에서도 돌아갈 곳이 명확하다.
- 새로고침·뒤로가기·알림 딥링크·탈퇴/위임 후 오래된 화면에서도 잘못된 팀/권한으로 작업하지 않는다.

### 매칭 필수 시나리오

- 모집 없음/서비스 오류/신청 닫힘/모집 중/배정 중/진행 중을 혼동하지 않는다.
- 선호·사진 분석 준비·보증금·배정·만남 진행의 실제 상태가 일치한다. mock 결과와 실제 거래를 구분한다.
- 중복 클릭·결제 복귀·동시 요청·수용 인원 부족·미납·마감·취소 때 접수/배정/원장이 꼬이지 않는다.
- 매칭 채팅은 허용 시간·참가 상태·동의 조건 전후를 각각 시험한다. 모임처럼 무조건 즉시 열리지 않는다.
- 기존 5회 후속 안내로 이어지고 미동의 자동 참가·연락처 공개는 없다.
- 새 로그인 후 원래 신청 화면으로 돌아오며, 오래된 localhost 쿠키가 있어야만 되는 상태를 완료로 부르지 않는다.

### 명령과 브라우저 근거

기존 package.json에서 확인한 후보 명령이며 이번 계획 턴에는 실행하지 않았다. 실행 전 fixture·쓰기 대상과 테스트 출력 폴더를 확인한다.

```text
npm run typecheck
npm run test:matching
npm run test:config
npm run test:deposit-security
npm run test:ui-cohesion
npm run check:secrets:all
npx tsc -p tests/matching-focused/tsconfig.json
node --test .tmp/matching-focused-tests/tests/matching-focused/*.test.js
```

추가로 `tests/meetups/league-*.test.mjs`, `candidate-*.test.mjs`, `tests/notifications/candidate-join-results.test.mjs`, `tests/matching/calendar-*.test.mjs`와 `event-calendar-*.test.mjs` 중 변경 관련 시험을 선택한다. 필요 시 새 회귀 테스트를 먼저 추가한다.

- 모바일 390×844·작은 화면·데스크톱에서 실제 클릭, 입력, 화면 이동, 포커스, 버튼 가림, 긴 팀명, 빈 목록, 오류·로딩을 확인한다.
- 승인 시안과 구현 캡처를 같은 상태에서 비교한다. 지도·사진·티어 심벌은 기존 자산을 재사용한다.
- 작은 레이아웃 조정과 별개로 이 묶음은 신청·금융·권한 위험이 있어 실행 시 `quantum-change-review`에 따른 독립 검토를 진행한다.
- 브라우저 HTTP 200·단위 테스트만으로 실기기 알림/실결제/운영 스케줄러 검증을 대신하지 않는다.

## 8. 권한·남은 의존성과 보고 방식

이번 계획으로 하지 않은 것: 소스 구현, 테스트 실행, DB 쓰기, SQL 적용, 실제 신청·알림 발송·결제, stage/commit, main 병합, push, 배포.

디자인은 승인됐으므로 다시 선택받지 않는다. 데이터 변경·원격 적용·실결제·배포가 필요해지는 단위에서만 정확한 대상과 영향을 제시하고 별도 승인을 받는다. 새 금액·몰수·채팅 시간·미확정 5회 콘텐츠 같은 제품 결정이 필요한 경우 해당 부분만 멈추고 나머지 독립 작업은 계속한다.

최종 구현 보고는 A 리그 / B 오늘밤 / B 캘린더·커플 / 공통 금융·알림으로 나눈다. 각 항목에 변경 내용, 통과 시나리오, 실패·수정 내용, 전후 캡처, 로컬과 운영의 미검증 범위를 표시한다. 사용자 확인용 로컬 주소와 실행 중인 작업본도 함께 적는다.

완료 목표는 ‘화면이 보인다’가 아니라 **기존 참가자가 자신의 현재 상태에서 다음 행동을 끝까지 이어갈 수 있고, 기존 기능과 금융·권한 규칙이 유지되는 것**이다.
