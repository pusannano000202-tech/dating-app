## 1. 사용자 결정과 이번 권한 범위

### 확정된 새 방향

- 업장이 매일 수용 팀 수를 먼저 입력해야 예약이 가능한 방식 대신, 퀀텀이 실제 팀·인원·방문 시간을 담아 요청하고 업장이 답한다.
- 예: 19시, 팀당 5명인 5팀을 요청하면 업장은 전부 또는 3팀만 수락할 수 있다. 15팀·5명은 설명 예시이지 고정 규칙이 아니다.
- 업장에서 퀀텀 A팀/B팀/C팀을 식별해 테이블로 안내할 수 있어야 한다.
- 오늘밤 매칭뿐 아니라 보이스 후 만남, 학과 대항전 후 회식, 일반·스터디 모임의 장소 예약에 같은 기능을 사용한다.
- 기존에 바꿀 부분, 새로 만들 부분, 업장 계정 권한을 설명하고 계획서를 작성한다.

최초 계획 작성 단계에서는 이 문서만 작성했으며 앱 소스 수정, 계정/권한 부여, 실제 예약 전송, 스키마 생성·적용, 결제·환불, stage·commit·push·main 병합·배포를 하지 않았다. 이후 같은 날 사용자가 성준/유저 분업과 두 작업 브랜치·인수인계 문서의 commit·push를 별도 승인했다. **현재 Git 공유 승인 범위는 [인수인계 §1](../handoff/active/QUANTUM_USER_PARTNER_HANDOFF_2026-09-20.md#1-브랜치와-승인-범위)을 따른다.** 앱 구현·DB 적용·실제 예약·결제·main 병합·배포 승인은 추가되지 않았다.

이 문서가 새 **업장 예약 방향**의 기준이다. `2026-09-19-league-matching-integration.md`의 사전 업장 수용량을 신규 매칭의 필수 전제로 삼는 부분은 이번 사용자 결정으로 대체된다. 현재 코드가 이미 바뀌었다는 뜻은 아니다. 그 외 사람 매칭, 선호 순위, 보증금·채팅·동의·개인정보 규칙은 유지한다.

기존 금융/모집 결정은 `docs/implementation/social-scenes/GUIDED-PARTICIPATION-DECISIONS-20260912.md`, 공유 경계는 `docs/handoff/active/COLLABORATION_BRANCH_2026-09-20.md`와 `docs/engineering/INTERFACE_CONTRACT.md`를 참조한다. 별도 문서에 새 요구사항을 중복 작성하지 않는다.

### 승인되지 않은 세부 사항은 제안으로 분리

아래의 미수락 팀 재요청 순서, 조건 변경 동의 방식, 응답 제한시간, 요금·취소 정책, 직원 세부 권한은 구현 제안이다. 예약 방향 승인을 금융 정책·자동 재예약·연락처 공개 승인으로 해석하지 않는다.

### 같은 날 추가 요구 — 시간 안내·좌석 스케줄·담당 분업

- 변경 제안이 19:30이면 사용자에게 즉시 `19:30 보드게임으로 변경 제안`을 안내하고, 필요한 확인 후에만 `19:30 보드게임 예약 확정`으로 표시한다. 원 요청 19:00, 제안 19:30, 확정 시각을 별도 보존하며 모든 화면/알림은 같은 예약 revision을 읽는다. 단순 시각 복사나 예약 확정으로의 무동의 전환은 하지 않는다.
- 업장은 테이블 위치·이름·수용 인원을 등록하고, 날짜/시간별 예약을 해당 테이블에 배치해 볼 수 있어야 한다. 사전 일별 수용 팀 수 강제와 테이블의 기본 공간 정보 등록은 별개다.
- 추천 UI는 `매장 좌석 배치 보기 ↔ 시간표 보기` 전환이다. 시간표는 행=테이블, 가로=시간으로 확정/임시 확보/이용 중을 구분한다. 모바일은 테이블 선택→시간 목록으로 조작 가능하게 한다. 끌어놓기 외에도 팀 카드의 `자리 배정/변경` 버튼을 제공한다. 실제 디자인/구현은 미완료다.
- 같은 시간대의 두 예약을 한 테이블에 덮어놓지 못하게 한다. 테이블을 옮겨도 예약 시간·인원은 그대로이며, 시간 변경까지 필요하면 다시 조건 제안 절차를 따른다. 이미 사용 중인 테이블 삭제는 차단하고 사용 종료 후 비활성화한다. 외부 전화 예약/일반 방문의 사용 시간도 수동 차단할 수 있게 제안하되 POS 자동 연동 완료로 표현하지 않는다.
- 성준이 업장·관리자 쪽, 본 작업은 사용자 앱을 맡는다. [인수인계](../handoff/active/QUANTUM_USER_PARTNER_HANDOFF_2026-09-20.md)에 작업 브랜치·기존 초안 코드·공용 전달 계약과 시험을 정리한다. 신규 예약 구현·DB 적용 승인은 이번 Git 공유와 별개다.

## 4. 예약의 단위와 추천 흐름

### 4.1 팀과 예약을 분리

- `팀 구성 완료`: 함께 갈 사람이 정해짐. 업장이 확정된 상태가 아니다.
- `예약 요청 중`: 요청한 업장의 답을 기다림.
- `조건 확인 필요`: 업장이 시간/가격/좌석 조건을 바꿔 제안함.
- `예약 확정`: 특정 팀/동행 인원에 대해 업장·시간·조건이 양쪽에서 일치함.

오늘밤은 기존 사람 매칭과 1·2·3순위 결과를 유지한다. 단, 공급량에 묶인 활동 확정 시점은 달라져야 한다. 새 경로에서는 우선 **희망 활동**으로 표시하고 예약 확정 전에는 실제 업장 확정처럼 말하지 않는다. 공급 부족 때문에 다른 활동·가격·시간으로 바뀌면 해당 조건에 대한 동의 없이는 이동시키지 않는다.

기존 회차·금융 규칙의 납부 확인을 통과한 팀부터 업장 요청 가능하게 하되, 새로운 예약을 이유로 보증금을 추가 청구하거나 환불/이월 시점을 바꾸지 않는다. 보이스·회식·장소 예약에 새 보증금을 적용할지는 별도 결정이며, 현재 모임 보증금을 자동으로 전용하지 않는다.

### 4.2 오늘밤의 5팀 요청→3팀 수락 예시

1. 15팀이 구성됐다면 각 팀의 희망 활동을 집계한다. 보드게임 5팀·술집 5팀 등은 결과 예시이며 5/5/5로 강제 분배하지 않는다.
2. 제휴·영업·활동 적합성·주소 검증이 확인된 업장 중 요청 대상을 고른다. 일별 사전 수용량이 없어도 요청할 수 있다. 영업시간·예약 가능 여부·업장 이용 조건 등록까지 없애는 것은 아니다.
3. 업장에는 `19:00~21:00 / 5명씩 5팀 / 총 25명 / 응답 마감`을 표시한다. 시작 시간뿐 아니라 이용 종료 시각 또는 예상 이용 시간도 포함한다.
4. 사장님은 `5팀 전부 수락`, `일부 수락`, `다른 조건 제안`, `거절` 중 하나를 선택한다.
5. `3팀 수락`이면 서버가 요청 생성 때 저장한 순서대로 적합한 3팀을 지정한다. 그 3팀과 총 15명을 보여주고 최종 수락한다. 임의의 외모/성별/프로필로 골라 받지 않는다.
6. 승인된 3팀만 해당 업장 예약 확정. 나머지 2팀은 `이번 업장 미수락`이며 확정 3팀의 예약·채팅·보증금은 건드리지 않는다.
7. 남은 2팀은 동의한 조건 범위 내 재요청 대상이 된다. 초기에는 운영자 확인 후 다른 제휴 업장에 순차 요청하는 안을 추천한다. 자동 재요청은 사전 허용 범위와 마감/최대 시도 횟수를 확정한 뒤 별도 활성화한다.
8. 미수락 팀을 무한히 기다리게 하지 않는다. 응답·전체 탐색 마감 뒤 `예약을 확보하지 못했어요`와 취소/반환 신청 안내를 제공한다. 확정되지 않은 장소로 출발시키지 않는다.

팀 인원은 5명 고정이 아니다. 5명/6명 팀이 섞이면 인원별 수락 가능한 구성과 합계를 명시한다. **3팀 수락은 3명 수락이 아니고, 팀 구성원을 쪼개 다른 업장으로 보내지 않는다.** 일반 회식은 `12명 한 일행`처럼 요청하며 별도 동의 없이 여러 일행으로 분할하지 않는다.

한 업장 응답에서 수락하지 않은 나머지를 계속 잡아두지 않는다. 미수락 단위는 원 요청에서 명시적으로 종료한 뒤에만 다음 요청을 만든다. 이전 업장의 늦은 수락은 거절한다.

### 4.3 시간 변경과 양쪽 확인

요청이 19시이고 업주도 19시 3팀을 수락했다면 조건이 동일하므로 선택된 3팀만 확정할 수 있다.
반면 19시 요청에 업주가 19시 30분을 제안하면 `업장 제안 / 아직 예약 미확정`이다.

추천안: 오늘밤 매칭은 변경된 조건으로 갈 팀원 모두가 확인한 뒤 확정한다. 보이스·회식·모임은 먼저 동행 참여자와 예약 대표자를 지정하고, 위임받은 조건 범위만 대표자가 확정한다. 범위를 벗어난 시간·가격·활동 변경은 동행자 재확인 대상이다.

업장 제안은 유효기간 동안 해당 자리/시간을 임시 확보한 조건이어야 한다. 수락 순간까지 같은 자리를 다른 요청에 다시 주지 않는다. 만료·거절 시 임시 확보 해제, 마지막 참가자 동의와 만료가 경합하면 서버 시각/트랜잭션으로 한 결과만 확정한다.

## 5. 네 출발점, 하나의 예약 기능

| 출발점 | 사용자 진입 | 예약에 전달할 대상 | 보존할 기존 기능 |
| --- | --- | --- | --- |
| 오늘밤 | 팀 구성 결과의 `업장 확인 중/예약 보기` | 확정된 팀 단위, 희망 활동, 회차 시간, 기존 자격·보증금 상태 | 사람 매칭, 3순위, 친구 묶음, 준비/채팅 공개 시점, 안내·투표 |
| 보이스 | 대화 화면의 `직접 만나기` | 실제 동의한 동행자, 대표자, 희망 장소·시간 | 음성 통화 상태와 개인정보 경계. 음성방 전체 자동 참석 처리 금지 |
| 학과 대항전 | 팀/경기 채팅의 `경기 후 모이기` | 우리 팀 또는 동의한 양 팀 중 실제 참여자, 회식 시간 | 경기·소속 팀·점수·복수 팀 참가 규칙. 경기 결과를 예약으로 덮지 않음 |
| 모임·스터디 | 모임 채팅/상세의 `장소 예약` | 동의한 참석자와 모임 회차, 장소 조건 | 방장 승인·보증금·일정 투표·채팅. 공개 모집 회원 전체를 자동 예약하지 않음 |

사용자 경로: `동행 확인 → 업장/시간/조건 선택 → 요청 내용 확인 → 업장 응답 대기 → 예약 카드`.
예약 대표자 한 명이 전송하며 다른 동행자가 동시에 눌러도 같은 예약을 중복 생성하지 않는다. 대표자 변경과 취소 권한은 이력으로 남긴다.
음성 통화 종료·방 종료·대표자 탈퇴 후에도 이미 만든 예약은 잃지 않는다. 활성 예약은 별도 영속 ID와 참여 스냅샷으로 내 예약에서 조회하며, 대표자 위임/예약 취소 동선을 제공한다. 권한 없는 과거 방 멤버가 이후 예약 정보를 계속 읽을 수 없도록 별도 예약 멤버십을 검사한다.

## 6. 추천 화면 구성과 핵심 상호작용

한 화면에 정보/버튼을 모두 쌓지 않는다. 업장 홈은 **새 요청 / 확정 예약 / 실적** 세 구역, 사용자 측은 기존 채팅에 예약 카드 하나와 상세 화면을 둔다.

### 업장 요청 상세 — 텍스트 와이어프레임(실제 캡처 아님)

```text
← 새 예약 요청                    응답 마감 18:50
오늘 19:00–21:00 · 보드게임
5명 × 5팀                         총 25명
요청 조건 · 예상 이용 시간 · 팀별 인원

[5팀 전부 수락]
[일부만 받을게요]  → 받을 팀 수/인원 확인 → [3팀 수락]
다른 시간·조건 제안                  거절
```

- 부분 수락 최종 버튼은 `3팀 · 15명 수락`처럼 결과를 밝힌다.
- 조건 변경은 별도 짧은 화면에서 다룬다. 제안을 보낸 것을 예약 확정으로 표시하지 않는다.
- 전송 실패/네트워크 끊김은 최신 결과 재조회. 버튼을 다시 눌러 새 요청을 만드는 방식으로 복구하지 않는다.
- 빈 요청함은 `새 예약 요청이 아직 없어요`; 오류를 0건으로 표시하지 않는다. 상세에서 뒤로 가면 원래 필터·스크롤로 복귀한다.
- 수락 전 나가기는 저장된 초안을 유지할 수 있지만 예약을 전송하지 않는다. 수락 후 취소는 사유·영향 확인을 포함한다.
- 업장 요청 접수→배지/알림음(사용자 허용 시)·기기 알림→응답 마감 전 리마인드. 알림을 열지 않았다고 자동 수락하지 않는다.

### 현장 안내

```text
오늘 확정 예약
19:00  퀀텀 A팀  5명  2번 테이블  도착 전
19:00  퀀텀 B팀  5명  4번 테이블  도착 전
19:00  퀀텀 C팀  5명  안쪽 단체석  도착 전
```

- 표시용 A/B/C 외에 예약별 변하지 않는 식별자와 짧은 확인 코드를 함께 사용한다. 날짜/업장/시간이 다른 A팀과 혼동하지 않는다.
- 테이블 번호가 없는 업장은 `창가석`, `안쪽 단체석`, `직원에게 확인` 등으로 안내한다. 테이블 미지정을 예약 미확정과 혼동하지 않는다.
- 한 일행이 두 테이블을 함께 쓰는 경우도 지원한다. 겹치는 시간에 같은 테이블을 중복 배정하지 않는다. 매장 내 실제 배치는 업장이 최종 확인한다.
- 참가자에게 `예약 확정 · 19시 · ○○보드게임 · 퀀텀 A팀 · 2번 테이블` 카드를 보여준다. 좌석 변경은 최신 revision으로 갱신한다.
- 업장에 필요한 것은 팀 코드·시간·인원·이용 조건이다. 얼굴 사진, 연애 상태, 외모 점수, 사적인 채팅, 개인 결제 원장은 공유하지 않는다. 앱 내부 문의 수단을 우선한다.
- 도착 체크는 서비스 제공/정산 확정과 별도다. 업장의 한 번 클릭으로 이용자 보증금 몰수·환불을 실행하지 않는다.

## 7. 업장 로그인·권한 설계

기존 Auth/초대/승인 기반을 재사용한다. 새 업장 등록 단계의 사업자·실제 담당자 확인은 운영 절차로 명시하고, 자동 검증 API가 이미 있다고 가정하지 않는다.

`운영자 제휴 업장 등록·확인 → 대상 계정 지정 초대 → 업주 본인 로그인·초대 수락 → 최고관리자 승인 → 내 업장 선택 → 예약 요청함`.

현재 초대 API는 이미 존재하는 사용자 ID를 대상자로 받는다. 따라서 신규 업주라면 먼저 일반 가입/계정 확인이 필요하다. 이메일만 입력하면 자동 가입·초대 발송된다고 설명하지 않는다. 토큰은 만료·단회 사용·대상 일치 검사, 로그/분석 도구 유출 방지가 필요하다.

| 역할 | 제안 권한 | 허용하지 않을 것 |
| --- | --- | --- |
| 사장님 owner | 본인 업장 예약 수락·거절·좌석·실적·약정 비용 조회 | 다른 업장 정보, 이용자 보증금 처리, 자신의 상위 권한 부여 |
| 직원 staff | 허용된 업장 예약 접수·좌석·도착/서비스 확인 | 매출/정산·계약 단가·직원 권한 변경(기본 차단) |
| 운영 관리자 | 미응답/예약 실패 대응, 감사 가능한 예약 지원 | 임의 환불·상위 권한·민감 프로필 열람 |
| 최고관리자 | 검증된 업장 멤버십 승인/회수, 민감 설정 관리 | 감사 기록 없는 대리 수락·원장 덮어쓰기 |

초기 직원 추가도 기존의 검증/승인 절차를 유지한다. 사장님의 직원 초대 기능이 필요하면 별도 위임 범위로 제한한다. 여러 가게를 운영하는 계정은 매장 선택 후 해당 매장 권한을 매 요청마다 확인한다.
직원 회수/퇴사·업장 정지 뒤 오래된 로그인 토큰이나 열린 화면으로도 변경하지 못하도록 현재 DB membership을 재확인한다. 민감 설정 변경은 재인증·감사 이력 대상으로 한다.

## 8. 개발 계약 초안 — 공통 예약 엔진

아래 이름은 신규 설계안이며 현재 테이블/API가 존재한다는 뜻이 아니다. 기존 공용 타입을 즉시 바꾸지 않는다.

- **예약 동행 단위**: 원본 종류/ID(오늘밤 팀, 음성 세션, 경기/팀, 모임 회차), 대표자, 실제 동의한 참여자, 인원·요청 조건 스냅샷, 정책 버전.
- **업장 요청**: 대상 업장, 예약 단위 목록, 방문 시간 구간, 비용/이용 조건, 응답 기한, 현재 revision, 요청 방식 버전.
- **업장 응답/조건 제안**: 수락할 단위·인원, 변경 조건, 유효기간, 처리 계정. 요청 1개에서 각 단위별 결과를 확정하고 잔여 단위를 종료.
- **확정 예약·좌석**: 동행 단위별 업장·시간·조건·팀 코드, 테이블 연결, 도착/서비스 상태.
- **예약 이벤트·알림 outbox**: 누가/언제/어떤 revision을 변경했는지, 중복 방지 키, 알림 수신 대상/재시도/만료.
- **금융 연결 참조**: 기존 활동 보증금 ID, 추후 증빙된 매출/취소/이용료 기록. 예약 상태에 돈의 상태를 합치지 않음.

신규 모듈 후보: `lib/reservations/`, `components/reservations/`, `app/api/reservations/`, `app/api/partner/reservations/`, `app/partner/reservations/`. 새 구현 승인 후 정확한 파일 목록·권한·입출력 계약을 고정한다.

핵심 불변 조건:

1. 동일 동행 단위·방문 구간에 활성 업장 요청/조건 제안/확정 예약은 하나만 존재. 일반 사용자의 여러 모임·여러 팀 소속을 금지하는 전역 제약은 만들지 않음.
2. 같은 멤버들이 서로 다른 출발 화면에서 동일 방문을 중복 요청하는 것도 탐지한다. 실제 참가자별 겹치는 방문 구간은 기존 예약으로 안내하고 조정 후 진행하며, 팀 소속 자체는 유지한다.
3. 대상 수락·만료·취소·재배정은 DB 트랜잭션/행 잠금, revision, 멱등키로 검증. 재시도에 같은 키를 사용하고 payload가 다르면 충돌 처리한다.
4. 업장·시간·좌석 임시 확보는 하나의 재고/확정 원장으로 경쟁을 제어한다. 일별 수용량 선입력 의무가 없다는 이유로 초과 수락을 허용하지 않는다. 테이블 정보가 없는 가게는 수락 화면에 겹치는 기존 확정·임시 확보 예약을 반드시 보여주고 인원/공간 확인을 받는다. 외부 전화/방문 예약까지 자동 파악한다고 주장하지 않는다.
5. 생성 시 서버가 원본 방/팀의 최신 참여 자격·동행 동의·대표권을 확인한다. 생성 이후 조회·취소·위임은 **현재 예약 멤버십·대표권**으로 판정한다. 원본 방 종료나 음성 통화 나가기는 예약 참가 철회가 아니며, 예약 탈퇴/취소는 별도 명시 동작이다. 새 동행자 추가 시 그 사람의 참여 자격·동의를 확인하고 예약 revision을 갱신한다. 계정 정지·예약 권한 회수·필수 금융 조건은 생성 후에도 해당 변경 시 재검증한다. 클라이언트가 전달한 다른 방 ID/멤버/인원을 신뢰하지 않는다.
6. DB/RLS와 API 모두 업장별/예약별 권한을 제한한다. `user_metadata` 또는 화면 탭만으로 권한 판단하지 않는다. 비밀 키·정산 원장은 클라이언트에 노출하지 않는다.
7. 알림은 저장된 예약 이벤트를 근거로 발행. 전송 지연·중복·권한 회수·수락 후 옛 알림 클릭에도 최신 상태를 보여준다. 잠금화면에 민감한 만남/개인 정보를 보내지 않는다.
8. 팀 인원 증감·탈퇴·일정 변경은 예약 revision을 올리고 업장과 당사자의 재확인 대상으로 한다. 이미 확정된 인원/조건을 몰래 바꾸지 않는다.
9. 예약 후 업장 취소는 취소 사실을 즉시 알리고 대안 제안/운영 지원으로 연결한다. 손해배상·위약금·보증금 몰수는 새로 승인하지 않는다.
10. 월별 통계는 같은 예약의 재시도·재배정·알림을 새 실적으로 세지 않는다. 예약 생성/방문 완료/매출 발생 월과 타임존을 구분한다.
11. 인증된 계정도 무제한 요청하지 못하도록 계정·동행 단위·업장별 속도 제한과 활성 요청 한도를 둔다. 구체 한도는 운영 설정이며 무작위 업장 대량 발송은 지원하지 않는다. 요청함은 매장/상태/시간 인덱스와 페이지 단위 조회를 사용하고 갱신 실패 시 제한된 재시도를 한다.

상태 표시: 단위별 `초안 → 요청 중 → (변경 제안 확인) → 확정 → 도착 → 이용 완료`, 별도 종료 `거절/기한 만료/취소`.
요청 묶음의 `부분 수락`은 집계 상태이고 모든 동행 단위가 확정됐다는 뜻이 아니다. 대안이 없으면 미확정으로 종료하며 이미 확정된 다른 단위는 유지한다.

## 9. 월별 실적·돈의 범위

먼저 예약 건수·실제 방문 팀/인원·취소율·매칭/보이스/리그/모임 유입 출처를 집계한다.
매출은 거래 증빙이 있을 때만 `확인된 매출`, 사장님 입력은 `입력 매출`, 인원×객단가는 `추정`으로 구분한다. 업장 전체 매출이나 순수 증가 매출로 부풀리지 않는다.
단가·정률 수수료·청구 방식·PG/POS 연동은 미결정이다. 이번 계획에서 요율이나 자동 출금을 정하지 않는다. 현장 결제와 앱 결제의 돈 흐름, 취소/환불 조정, 원거래별 비용 계약 버전을 별도로 설계한다. 사용자의 보증금은 업장 매출/퀀텀 수익과 분리한다.

## 10. 구현 순서·협업 경계

| 단계 | 작업 | 주 소유 범위(협업 제안) | 끝났다고 판단할 조건 |
| --- | --- | --- | --- |
| P1 | 상태·예약 단위·권한·부분 수락 계약과 추천 화면 확정 | 공용 설계 담당 1명 | 5→3+2, 시간 제안, 취소/만료를 사용자·업장 양쪽으로 설명 가능 |
| P2 | 공통 예약 저장/API/RLS·동시성·알림 원장 | 공용 서버 담당 1명 | 실제 독립 DB 세션의 경쟁 시험·타 업장 차단·복구 통과 |
| P3 | 업장 요청함·부분 수락·좌석·권한 화면 | 친구분: `app/partner/`, 업장 컴포넌트와 승인된 API | owner/staff 실계정으로 접수→수락→안내, 모바일/데스크톱 클릭·캡처 |
| P4 | 오늘밤 팀 구성과 예약 연결 분리 | 우리 쪽: 매칭 화면/adapter, 서버 담당과 계약 공유 | 기존 매칭·순위·공개시점·금융 회귀 + 5팀 요청 부분 수락 완주 |
| P5 | 보이스·리그·모임 입구 연결 | 우리 쪽: 각 출발 화면과 adapter | 실제 동행 동의·대표권·통화 종료 후 예약 유지 검증 |
| P6 | 업장 월별 방문 실적, 매출 증빙 연결 설계 | 친구분 대시보드 + 공용 집계 담당 | 취소/재요청 중복 없음, 확인/입력/추정 매출 구분 |
| P7 | 독립 검토·회귀·사용자 시연·이관 검증 | 고정된 후보를 독립 검토 | 보안·실동선 증거와 미검증 운영 조건을 구분한 보고 |

P3와 P4는 P2 계약을 공유한 후 분리 진행 가능하다. 친구분에게 DB 타입/권한을 일방적으로 맡기고 우리 쪽이 별도 버전을 만드는 방식은 피한다. 공용 DB/API/타입/금융/알림은 **한 명의 변경 책임자**를 정하고 다른 쪽은 합의한 계약으로 연결한다. 같은 파일 동시 수정은 하지 않는다. 최초 계획 작성에는 담당자 배정·새 브랜치 생성·공유 push가 포함되지 않았으나, 이후 성준/유저 담당 분리와 두 브랜치 공유는 별도 승인됐다. 공용 변경 담당자 지정 등 최신 협업 경계는 인수인계를 따른다.

### 기존 기능을 보존하는 전환

- 기존 회차는 기존 프로토콜로 종료, 새 회차/예약에만 서버가 고정한 새 버전을 적용한다. 클라이언트가 버전을 골라 금융/권한 검사를 우회하지 못하게 한다.
- **전환 순서:** 신규 생성 기능을 닫은 상태에서 DB/RPC에 구·신 데이터의 버전 방어를 먼저 마련한다. 구 실행기를 중지·교체하고 모든 조회/쓰기/재시도 경로의 버전 범위를 검증한 뒤 신규 회차·예약 생성을 연다. 실행기 수정만 믿지 않고 구 RPC 호출도 새 예약을 변경할 수 없도록 저장 계층에서 거부한다. 구 작업의 지연 재시도나 앱 코드 롤백에도 이 방어는 유지하며, 이미 열린 신규 예약의 처리기를 없애지 않는다. 각 migration/운영 실행기 전환은 별도 승인 단계다.
- 격리 작업본에서 신규 필드/테이블·adapter를 추가하고, 과거 데이터 삭제나 일괄 덮어쓰기를 하지 않는다. 옛 수용량 데이터는 과거 예약 조회에 보존한다.
- 테스트에서만 읽기 전용 비교 실행을 한다. 구·신 발송기/예약기/정산기를 동시에 실행해 예약·알림·청구를 두 번 만들지 않는다.
- 준비가 안 되면 새 경로를 비활성화하고 사유를 표시한다. 새 방식으로 생성된 진행 중 예약은 비활성화 뒤에도 조회·취소·처리할 수 있게 유지한다. 구 방식으로 강제 되돌리거나 방을 재생성하지 않는다.
- 신규 버전은 공통 저장/P2부터 검증하고 오늘밤 한 출발점에서 끝까지 연결한 뒤 확장한다. 네 개 독립 예약 엔진을 만들지 않는다.

## 11. 필수 시험과 검증 방법

1. 5명×5팀 요청→3팀 수락→3팀 15명만 확정, 2팀은 다른 업장으로 재요청 가능. 총 25명 유지, 중복/누락 없음.
2. 5/6명 혼합 팀, 12명 회식 한 일행, 2테이블 사용. 지원하지 않는 인원 조합을 명확히 거절하고 팀을 쪼개지 않음.
3. 19시 요청에 19시30분 제안→참가자 확인 전 미확정. 일부 미동의·확인 만료→자리 해제, 이전 조건으로 자동 확정 금지.
4. 두 직원 동시 수락·동시 좌석 배정, 취소와 수락 경합, 만료 후 늦은 수락, 권한 회수와 응답 경합, 네트워크 응답 유실 재시도.
5. 서로 다른 업장/학교/팀 ID 조작, 임의 대표권, 기존 JWT로 회수 권한 재사용, 사용자→partner 자기 승격, 통계의 다른 매장 유출 차단.
6. 보이스 방 종료/참가자 이탈·대표자 탈퇴 후 예약 복귀; 실제 동의 없는 사람을 인원에 포함하지 않음.
7. 사용자·사장님·직원·관리자의 같은 예약 ID/팀 코드/시간/좌석/revision 확인. 허용 역할만 조작 가능.
8. 업장 미응답·거절·확정 후 취소·조회 장애. 실패를 0건/예약 확정/환불 완료로 표시하지 않음.
9. 기존 홈·매칭·커뮤니티·모임·팀 채팅·투표·캘린더·연애 상태·복수 팀 가입·보증금 환불/이월 경계 회귀.
10. 모바일 390px와 데스크톱: 긴 업장명·다수 팀, 스크롤/키보드, 뒤로 가기, 알림에서 복귀, 중복 탭, 큰 버튼·상태 문구 구분. 수정 화면 캡처 제출.
11. 알림 권한 허용/거절, 앱 전경/백그라운드·로그아웃/계정 전환, 실제 휴대폰 수신. 전송 성공 응답과 실기기 도착 증거를 분리.
12. 재시도·취소·다른 업장 재예약이 월별 실적을 중복 증가시키지 않는지, 월말 KST 경계·지연 수정 이력·증빙 없는 매출 표시 확인.
13. 기존 회차와 신규 회차가 혼재할 때 구 배정/만료/공개/환불/정산 작업을 재시도해도 새 예약을 변경하지 못하는지 확인. 신규 생성 gate가 전환 검증 전 열리지 않는지, 롤백 뒤에도 신규 예약 조회·취소·마무리가 가능한지 검사.
14. 요청 한도·중복 전송·업장 대량 요청 차단과 실제 목록 페이지/상태 집계의 일치 검사. 접근할 수 없는 매장을 통계·오류 문구로 추측하지 못하게 함.

현재 package scripts에서 확인한 회귀 후보: `npm run test:auth`, `test:matching`, `test:config`, `test:deposit-security`, `test:voice`, `test:ui-cohesion`, `typecheck`, `build`. 구현 시 스크립트 부작용과 새 테스트 포함 여부를 확인하고 격리 작업본에서 실행한다. 현 `lint`는 `next lint` 스크립트이므로 실제 실행 가능성을 먼저 확인하고 통과한 것으로 가정하지 않는다.
신규 예약 테스트 디렉터리/실행기를 추가하고 Postgres 트랜잭션·RLS는 실제 격리 DB에서 검증한다. 단위 테스트나 정적 SQL 검사만으로 동시성/운영 권한 검증을 대체하지 않는다. 원격 적용·실결제·실기기·배포는 별도 승인/증거가 필요하다.

## 12. 운영 전 확정할 선택과 이번 결과

| 미결정 | 추천 초안 | 막는 단계 |
| --- | --- | --- |
| 업장 응답/조건 제안 제한시간·재요청 횟수 | 운영 시간대별 서버 정책, 미응답 종료·담당자 알림 | 실제 자동 예약 운영 |
| 남은 팀의 업장 선정/자동 재요청 허용 범위 | 초기는 운영자 확인 순차 요청, 다른 시간·활동·가격은 동의 | 무인 재배정 활성화 |
| 보이스/회식/일반 장소 예약의 추가 보증금 | 임의 신규 청구 없음, 기존 원장 재사용도 자동 처리하지 않음 | 새로운 유료 예약 정책 |
| 수수료·대금 흐름·매출 증빙 | 방문 실적 먼저, 매출/과금은 계약·증빙 후 연결 | 실제 청구·자동 정산 |
| 직원·대표자 위임 범위, 취소/노쇼 분쟁 기준 | 최소 권한·명시 위임·감사, 금전 제재 자동화 없음 | 권한 위임 확장·금전 조치 |

이 선택들은 계획서 작성을 막지 않는다. 구현 시 해당 위험 기능만 닫고 독립적인 화면/예약 상태/권한 시험은 진행할 수 있다. 기존에 결정한 요청·부분 수락 방향을 다시 묻지 않는다.

최초 계획 작성 결과: 계획 문서만 작성했고 앱 코드/DB/운영 계정/예약/결제/배포는 변경하지 않았다. 이후 추가한 요구사항과 Git 공유 승인 범위는 §1 및 인수인계에 구분했다. 아래 검증 기록은 최초 계획 문서의 검증이며 기능 구현 완료 증거가 아니다.

## 13. 최초 계획 작성 단계의 문서 검증 기록

- 작성 전 branch/HEAD/clean 상태 확인, 현재 source와 관련 migration·최신 금융 결정 대조.
- 공식 권한 참고: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). 화면 숨김이 아닌 행/업장별 권한 검사를 계획에 반영. changelog.md는 웹 도구의 콘텐츠 형식 오류로 읽지 못했으며 구현 전 재확인 대상.
- 최초 작성 당시 문서 내 실제 소스 참조 14개 존재 확인, 코드 블록 닫힘·후행 공백·문자 깨짐 검사. 당시에는 tracked/staged 소스 변경 없이 이 계획 파일 하나만 신규 작성했다. 이는 후속 Git 공유 변경 묶음에 대한 파일 수나 검증 결과가 아니다.
- 독립 계획 검토 1차: `REVISE`. G1~G6 범위는 포함됐으나 아래 두 경계 설명을 보완해야 한다는 판정. 실행 테스트 통과를 뜻하지 않는다.

| 검토 항목 | 실패 기준·원인 | 보완 전략 | 결과 |
| --- | --- | --- | --- |
| R1 / G2 | 원본 방의 최신 자격을 모든 예약 처리에 요구하면, 방 종료 후 예약 유지와 충돌 | 생성 시 원본 검사 / 이후 현재 예약 멤버십·대표권 검사로 구분. 원본 방 종료≠예약 철회 명시 | §8 조건 5에 반영, 독립 재검토 PASS |
| R2 / G5 | 신규 writer만 버전을 쓰면 구 cron의 광범위 조회/취소를 막지 못함 | 신규 생성 잠금→DB/RPC 방어→구 실행기 교체/검증→신규 개방. 구 재시도·롤백 혼재 시험 추가 | §10 전환 순서·§11 시험 13에 반영, 독립 재검토 PASS |

두 원인은 반증되지 않았으며 각각의 최소 수정으로 대응했다. 최종 독립 계획 검토: **PASS**, 추가 필수 수정 없음. 문서 일관성에 대한 판정이며 앱 구현·브라우저·DB·운영·보안 전체 검증을 뜻하지 않는다.
