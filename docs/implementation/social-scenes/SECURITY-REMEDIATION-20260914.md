# 보증금 보안 보완 실행 기록

기준: `8b90e9ae983fbd668512914bb10839ebd466d973` / `codex/web-security-main-20260914`.
사용자가 이전 보고의 세 문제 해결을 승인했다. 기존 3004/3010 원본은 보존하고 이 검증 작업공간에서만 수정했다. **판정: 세 금융 코드 결함 로컬 보완·검증 완료 / 운영·메인 적용 보류.** 실계정·실결제·운영 완료 증거가 아니다.

## 확정 범위

1. 일반 모임·스터디·멘토링: 기존 `refund_due` 장부 → 본인의 별도 반환 신청 → 운영자 확인 → 결제사 원결제 취소 → 증빙 확인 → 동일 장부를 읽는 사용자/운영자 완료 표시.
2. 탈퇴 요청 시 새 금융 장부를 보존 분류에 포함하고 최종 삭제 직전과 실제 DB 삭제 경계에서도 미정산 결제 문맥을 보호한다.
3. 기존 매칭의 전액/부분 PG 취소 결과가 반환 요청·보증금·수익 기록에 원자적으로 반영되고, 중복/역순 이벤트에 상태가 되돌아가지 않도록 한다.

금액은 기존 확정 10,000원 신규 결제 기준. 과거 금액 소급 변경, 새로운 몰수/출석/분쟁/이월 자격 정책, 모임 취소만으로 자동 송금, 실제 결제·환불/운영 DB/배포는 범위 밖이다. 기존 `held` 상태를 임의로 반환 가능 상태로 전환하지 않는다.

## 시험 환경과 단계

- 실패를 보여주는 시험 → 최소 구현 → 해당 회귀 → 서로 다른 경계의 독립 재검토 → 통합 타입/빌드/회귀.
- PG transport는 합성 응답만 사용한다. 실서비스 자격증명을 시험 프로세스에 넣지 않는다.
- SQL fixture는 인메모리 PGlite 및 별도 `postgres:17-alpine` 컨테이너에서 실행한다. 테스트 컨테이너는 `--network none`, 호스트 포트/바인드 없음, 사용자 데이터·운영 키 없음이다. 실제 앱 DB는 수정하지 않는다.
- 계정 삭제, matching webhook, admission refund는 각각 별도 테스트 DB를 사용한다. 생성/처리 경합은 가능한 경우 실제 PostgreSQL의 두 연결로 검증한다.
- 사용자/관리자 페이지에는 기존 디자인과 반환 상태 안내를 재사용한다. 조회 실패를 빈 장부나 반환 완료로 표시하지 않는다.
- 실계정/결제사 테스트 환경 왕복, 운영 DB 전체 적용·권한, 모바일 푸시·실제 카드 명세서 반영은 별도 미검증이다.

## 남은 외부 조건

보완 코드가 통과해도 현재 정적 migration 검사에 있던 66개 기존 경고를 통합 승인 근거로 숨기지 않는다. 최신 main 합성본과 운영 호환성은 별도 판정한다. 이번 구현 동의는 새 stage/commit/main/push/실제 금융 실행 승인이 아니다.

기존 화면/동선 파일 삭제 없음. 새 화면은 `/profile/deposits`와 `/admin/super-admin/meetup-refunds`. 마이의 기존 매칭 보증금 링크를 유지하면서 별도 모임 장부 링크를 추가했다. 관리자 승인은 ‘반환 대기’이며 PG 완료 증거가 있어야 ‘반환 완료’다.

### 독립 검토에서 추가 발견하고 고친 오류

- 일반 회원에 관리자 전용 최근 인증 RPC를 적용하던 HTTP 오류: 실패 재현 후 회원은 서버 인증된 최근 로그인, 관리자만 기존 MFA·최근 관리자 인증으로 분리했다.
- worker가 요청한 개수보다 많은 장부를 먼저 잠그던 SQL cursor 문제: 실제 PostgreSQL 두 연결로 재현하고 후보 쿼리 자체의 LIMIT/SKIP LOCKED로 수정했다.
- DB 결제확인 응답 유실로 `pending + payment_key NULL`인 정상 주문이 전액취소 웹훅에서 막히던 회귀: 정확한 원주문·소유자·전액취소 증빙일 때만 키를 복구한다. paid/held의 키 불일치나 부분취소는 허용하지 않는다.
- 자동 재시도 대기 상태와 관리자 ‘다시 처리’ 버튼 불일치: 승인·요청 ID·시도 횟수는 보존하고 pending+기록된 오류에 대한 명시 재시도를 허용했다. 실행 중 임대 탈취와 5회 한도 초과는 금지한다. 자동 처리 한도/계정 확인 필요 건은 UI에서 재시도 버튼을 숨긴다.

## 운영 반영 전 반드시 남겨둘 항목

1. **탈퇴 후 반환 복구 동선**: 이미 탈퇴 요청으로 제품 접근이 차단된 계정은 아직 하지 않은 참가 취소·본인 반환 신청을 수행할 경로가 없다. 특히 held 보증금은 실제 삭제 cascade가 차단되므로 자동으로 refund_due가 되지도 않는다. 이번 수정은 돈과 증거가 지워지는 것을 막지만 이 제품/운영 문제까지 해결한 것은 아니다. 동의 없는 반환 신청을 만들거나 삭제 계정의 인증을 풀지 않았다. 탈퇴 전 취소·반환 신청 안내/연결과, 기존 탈퇴 대기자의 본인 확인·의사 확인 복구 절차가 필요하다.
2. **실제 결제사 테스트 환경 왕복·실계정·운영 Supabase 전체 migration 및 RLS/권한·Auth 삭제·단말 알림·실제 카드 반영 미검증**. 합성 DB 시험을 이를 대신한 완료로 보고하지 않는다. Supabase CLI를 사용할 수 없어 14자리 UTC 이름의 새 forward migration 파일을 작성하고 격리 PostgreSQL에서 검증했다. 운영 DB advisor 검사는 수행하지 않았다.
3. **가동은 별도 승인**: `QUANTUM_MEETUP_REFUNDS_ENABLED`는 기본 비활성. 활성화에는 올바른 모드의 `TOSS_SECRET_KEY`, 충분한 `CRON_SECRET`, 서비스 클라이언트와 새 SQL이 필요하다. 내부 POST `/api/internal/meetups/refunds/process`는 인증 후 최대 2건씩 처리한다. 운영 스케줄러 등록·키 활성화·실제 취소를 이번 작업에서 하지 않았다. 체크아웃 활성화와 반환 활성화는 별개여서 신규 결제를 멈춰도 기존 반환은 별도로 운영할 수 있다.
4. source_room_id가 없는 과거 고아 기록이나 이미 이월 적용된 기존 매칭 보증금은 임의로 새 원거래에 연결하지 않고 정합성 확인 대상으로 남긴다. 재시도 한도 초과 건도 수동 원거래 검토가 필요하다.
5. 현재 main의 최신 변경과 합성·원격 CI·기존 66개 migration 경고의 해소/오탐 분류는 아직 별도 통합 게이트다. **메인 반영 준비가 완전히 끝났다고 보고하지 않는다.**

테스트 컨테이너 `quantum-financial-audit-20260914`는 network none·호스트 포트/바인드 없음·합성 자료만 사용했고 검증 후 중지했다. 삭제하지 않아 합성 재현 자료는 보존된다. 실제 앱의 DB/서버는 중지하거나 수정하지 않았다.

PG 응답 필드/원거래·취소 이력의 의미는 [토스페이먼츠 코어 API](https://docs.tosspayments.com/reference)를 확인했다. 이번 보완은 그 계약에 맞춘 로컬 코드 검증이지 결제사 상점 설정 검증은 아니다.
