## 배포를 막는 구체적인 문제

### 1. 운영 DB와 새 코드의 불일치

운영 migration 기록은 160개이며 마지막 버전은 `20260816092918`. 후보 SQL 파일은 274개다. 원격 main 대비 추가 187개는 커밋된 184개와 미커밋 3개다.

버전 숫자만 비교하면 162개가 일치하지 않는다. 그중 48개는 이름이 같은 운영 기록이 다른 타임스탬프로 존재하고, 114개는 정규화한 이름도 일치하지 않는다. **이 숫자는 실행해야 할 SQL 수가 아니다.** 같은 이름이 같은 내용을 보장하지 않으므로 일괄 재실행하거나 migration 기록만 강제로 맞추지 않는다.

운영 함수 카탈로그를 읽기 전용 조회하여 아래 8개 public 함수가 실제로 없음을 별도로 확인했다.

### 2. 필수 CI 검사기 보완

최초 `check:migrations`는 exit 1이었다. 경고 66개 중 50개가 기존 허용 기준과 일치하지 않았으며, 이는 전부 실제 SQL 결함을 뜻하지 않는다.

확인된 원인은 공백 없는 `AS(` CTE 선언, `preferences`/문자열 속 `REFERENCES`, 정상적인 인접 달러 태그 `end$fn$$ddl$;`의 오인식이다. `scripts/verify-migrations.py`와 CLI 회귀 테스트만 수정했으며 SQL 및 경고 baseline은 변경하지 않았다. 독립 검토에서 E 문자열 뒤 FK와 PL/pgSQL 본문 내부 인용 경계의 회귀 두 건을 찾아 RED 재현 후 보완·재검토했다. 최종 tooling 32개 통과, migration baseline 검사 exit 0, 기존 경고 10개 유지. 단순 경고 억제가 아니며 전체 PostgreSQL 문법 검사기나 DB 적용 증명도 아니다.

### 3. 운영 설정·실사용 검증 공백

- Google/Kakao가 켜져 있다는 사실과 앱에서 로그인 후 제자리로 돌아온다는 사실은 다르다. production 도메인·callback·공유 링크 returnTo를 확인한다.

- 공통 푸시와 새 모임 반환 worker는 운영 실행 주체·주기·인증 설정을 확인해야 한다. 내부 POST API가 있다는 이유로 자동 실행되는 것으로 보고하지 않는다.
- 보증금 대기판의 결제 미연결, 탈퇴 후 반환 복구 동선 등 기존 보고의 미해결 항목을 기능별 출시 게이트에 포함한다. 새 결제 기능 가동을 코드 배포에 자동 포함하지 않는다.

## 아직 필요한 제품 완성 작업

홈·마이·모임을 새 앱처럼 별도로 다시 만들지 않는다. 한 통합 후보에서 기존 기능을 보존하며 아래 순서로 하나씩 완성한다. 새 디자인은 추천 시안 1개를 확인받고 구현한다.

1. 모임의 핵심 한 바퀴: 신청자/방장/기존 멤버의 신청·보증금·알림·수락·채팅·종료·반환 상태를 같은 테스트 데이터로 검수한다. 운영 DB 정합성 확보가 선행되어야 한다.
2. 홈: 급한 다음 행동(신청 승인·미확정 일정·진행 중 약속), 참여 모임 사진 카드, 새 모임 발견 순으로 중요도를 정한다. 큰 상태 설명이 다음 행동을 밀어내지 않게 한다.
3. 모임: 둘러보기와 만들기 구분은 유지하되 단계마다 주요 버튼을 쉽게 찾도록 한다. 모집방/대기판의 신청 중·초대됨·합류됨 상태를 한 언어로 정리한다.
4. 마이: 프로필 요약, 연애 상태, 전체 보증금/반환, 내 활동, 계정 설정으로 역할을 나눈다. 매칭 보증금과 모임 보증금의 실제 장부는 분리하되 사용자가 찾는 입구와 상태 요약은 일관되게 제공한다. 언어·계정 관리가 첫 화면을 압도하지 않게 한다.

가장 빠른 완료 경로는 작업공간을 계속 늘리는 것이 아니라, 기준 통합 후보 + 검수용 DB + 요구사항별 완료 기준을 유지하는 것이다. 기능 하나의 양쪽 사용자 흐름과 모바일 캡처를 통과시키고 로컬 체크포인트를 남긴 후 다음 기능으로 넘어간다. 단위 테스트 성공을 실제 운영 완료로 바꾸지 않는다.

## 배포 후 반드시 확인할 사용자 흐름

1. 비로그인 공개 화면 → 카카오/구글 로그인 → 원래 열려던 모임·초대 링크 복귀. 신규 가입 및 기존 계정 모두 구분.
2. 홈·매칭·모임·커뮤니티·채팅·마이 접근과 하단 탭 소속 유지. 조회 실패를 빈 데이터로 위장하지 않음.
3. 학과 순위/모집방/대기판 → 신청·초대 → 방장 알림·방 공지 → 수락 → 신청자의 해당 팀 채팅 합류.
4. 일반 모임·전공 스터디·멘토링에서도 각 소속·채팅·보증금 상태가 정확히 연결됨. 내 메시지는 오른쪽, 입력창은 하단.
5. 사용자 보증금 장부와 관리자 장부가 동일 상태를 표시. 타인 조회·임의 금액·임의 반환 계좌·중복 정산을 거부.
6. 푸시는 앱 알림함과 별도로 실제 기기 수신·클릭 후 목적지 확인. 실제 결제사 왕복·금전 이동은 별도 승인된 시험만 실행.

## 복구·중단 기준

- 가입/로그인 또는 기존 결제 웹훅의 운영 호환성이 확인되지 않으면 배포하지 않는다.
- DB 변경은 되돌리기 쉬운 코드와 달리 기존 결제·회원 기록에 영향을 줄 수 있다. DROP/RESET으로 롤백하지 않으며, 사전에 이전 코드 호환성과 전진 수정 전략을 준비한다.
- 필수 검사 실패, 비밀값 노출, 권한 완화, 장부 불일치가 발견되면 운영 반영을 중단한다.
- 배포 성공 표시만으로 완료하지 않는다. 배포 SHA·실제 도메인·인증·주요 API·사용자 흐름 증거를 각각 남긴다.

## 실제 변경 및 미수행

- 변경: 준비 문서 유지·갱신, migration 검사기/회귀 테스트, 동일 DB 기반 일반 모임 HTTP 사용자 흐름 테스트 추가. 기존 금융 보완 39개 파일의 내용은 유지한다. 홈/마이 디자인을 새로 바꾼 작업은 아니다.
- 조회: 원격 Git ref/관계, GitHub Vercel 상태 기록, 운영 Supabase 제공자 설정·migration 기록·함수 존재 여부. 회원 개인 데이터 조회 없음.
- 검증: 금융 보완 39개 해시 일치, 새 빌드·회귀 검사와 모바일 화면의 실제 이동을 위 증거대로 구분했다.
- 로컬 저장: 금융 보완 39개 + 검사기/검사 2개 + 동일 DB HTTP 흐름 검사 1개 + 이 문서 1개의 명시적 허용 목록만 체크포인트 대상이다. QA 캡처와 임시 실행 파일은 Git에 넣지 않는다. Next dev가 자동 추가한 로컬 타입 경로는 제품 변경에 섞지 않는다.
- 미수행: main 병합/push/배포, 운영 DB·Auth 설정 변경, 실제 결제·취소·환불. 기존 원본 및 사용자 더티 변경은 보존한다.
