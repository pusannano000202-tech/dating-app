## 2. 최신 확정 동선 — 보증금은 참가 신청 안에서

모임 사진 선택 → 기존 방 보기 / 템플릿으로 방 만들기 → 참가 한마디 → 필수 보증금 금액·반환 조건 확인 → 새 결제 또는 자격 확인된 이월에 명시 동의 → 서버에서 보증금 확인 → 신청 접수 → 개설자 수락 → 확정 채팅.

사용자는 신청 과정에 보증금 단계가 보이지 않은 것을 명시적으로 잘못이라고 지적했다. 이전의 '개설자 수락 이후 보증금' 추천은 폐기한다. 모임 확인 단계부터 보증금 필요 여부가 보여야 하며, 신청 상태와 납부 상태는 별도로 표시한다. 결제 준비·확인 중을 납부 완료나 신청 접수로 표현하지 않는다. 금액·반환 정책·신청 만료 기간은 서버 정책으로 확정해야 하며, 미설정은 무료나 0원으로 대체하지 않는다.

첫 수직 구현은 실존 개설자와 방 ID가 있는 일반 사용자 개설 모임(`/meetups/[id]/apply`)이다. 스터디/멘토링 자동 모집을 공통 화면 링크만 바꿔 전환 완료했다고 주장하지 않는다. 새 금융 모델은 승인·거절·환불·검증된 PG 연동이 완성되기 전 실제 결제를 열지 않는다. 로컬 리허설의 금액과 승인·결제 결과는 명시적인 가상 예시다.

멘토링은 같은 구조에 멘토/멘티 자리만 추가하고 2+2 또는 3+3 구성을 보존한다. 학과 대항전은 기존 지도·포지션·티어·주장 승인 흐름을 확장한다. 매칭의 자동배정과 시간제 채팅은 별개로 유지한다.

홈에는 다음 행동 1개, 내 연애 상태, 보증금 요약을 보여준다. 상세 기능을 긴 한 페이지에 쌓지 않는다. 채팅은 항상 채팅 탭, 커뮤니티는 하위 콘텐츠에서도 커뮤니티 탭이다.

## 3. 보증금 안전 불변 조건

- 원입금 ID/결제 공급자 ID는 이월 후에도 추적 가능해야 한다. 활동 이름만 바꾸거나 과거 원장을 덮어쓰지 않는다.
- 동시에 서로 다른 활동 3개를 하면 각각 별도 잠금이다. 같은 1만 원을 3개 활동에 중복 예치할 수 없다.
- 종료·출석 확정·분쟁 없음으로 반환 가능해진 금액만 이월 후보. 이월은 사용자 최종 동의 후 원자적으로 해제+재배정.
- 환불 신청/처리 중 금액·분쟁 금액·예치 중 금액은 이월 불가. 환불/이월 동시 요청을 잠금과 멱등키로 차단.
- 사용자 화면의 반환 신청, 운영자 승인, PG 취소 처리, 공급자 취소 확인, 실제 결제수단 환급 시점은 구분한다. 공급자 취소 완료를 카드 명세서 반영까지 확인한 것으로 표현하지 않는다.
- 불참 신고는 검토 개시 근거이지 즉시 몰수 명령이 아니다. 판단 근거·당사자 소명·이의제기·승인자·시각이 연결돼야 한다.
- 모집 개설자는 방 참가 승인 권한만 갖는다. 보증금 몰수·환불 실행·상대의 다른 활동 금액 조회 권한은 없다.
- 자금 장기 보관/활동 간 이월은 PG 계약 및 적용 법적 요건 확인 전 운영에서 활성화하지 않는다.

금액 1만 원 및 시안의 인원·점수·음식 통계는 설명용 예시. 실제 정책/실데이터가 아니다. 2026-09-13 사용자는 보증금을 돌려달라고 신청하면 반환하는 방식으로 통일했다. 반환은 사용자 별도 신청으로 시작하며, 대기 취소·모임 종료만으로 자동 송금하지 않는다. 반환 자격·취소 유예·소명 기간·몰수 처리 기준을 이번 결정으로 임의 변경하지 않는다.

### 2026-09-13 반환 신청 공통 기준

- 적용 방향: 매칭·일반 모임·스터디·멘토링·학과 리그·합류 대기의 보증금 반환 개시 방식을 사용자 신청으로 통일한다. 각 화면/금융 처리기의 운영 반영 완료를 뜻하지 않는다.
- 활동과 납부 건을 명확히 선택해 반환 신청하고, 접수·처리 중·공급자 반환 확인을 분리한다. 반환 가능한 금액만 처리하며 같은 금액의 중복 신청/환불/이월은 막는다.
- 대기 취소는 글과 초대 종료이고, 보증금 반환 신청은 별도다. 신청하지 않았다는 이유로 다른 활동에 무동의 이월하지 않는다. 돈의 보관·처리 기한 등 운영 조건은 별도 검증 대상이다.
- 사용자가 반환 신청한 뒤 해당 보증금으로 대기 글을 유지하거나 새 참가에 재사용하지 못하게 금융 원장과 참가 상태를 함께 확인해야 한다.
- 실제 결제수단 반환이 확인되기 전 사용자·관리자 화면에 반환 완료로 표시하지 않는다. 기존 운영자 권한/감사/분쟁 규칙은 유지한다.
- 현재 작업은 결정 장부와 후보 화면 안내만 수정한다. 실제 반환 신청·PG 환불·원격 DB 적용·배포는 하지 않는다.

## 이번 신청 화면 구현 상태

### 추가 승인 범위 — 신청 소식과 기기 알림

- R18: 서버가 해당 방의 보증금 확인 → 신청 접수. 같은 트랜잭션에서 기존 멤버용 채팅 공지와 방장 개인 알림을 만든다. 소개·장점은 방장만 조회하고 공지/잠금화면에 노출하지 않는다. 방장 승인 시 정원·신청 revision·현재 권한을 재확인한 뒤 멤버십과 신청자 알림을 함께 저장한다. 신청 화면에서 승인 감지 시 해당 채팅으로 이동하고, 다른 화면에서는 알림을 눌러 해당 채팅으로 들어간다. 현재 참여자가 된 후 이전 대화 읽기가 가능해야 한다.
- R19: 공통 알림에서 별도 내구성 outbox를 만들어 명시적으로 구독한 기기로 Web Push를 발송한다. 재시도·만료 구독·로그아웃/계정 변경·중복 발송·권한 상실을 검사한다. 잠금화면에는 민감 정보 없는 일반 문구를 표시하고, 누르면 본인 알림함에서 현재 접근권한을 재확인한다. 기존 전용 푸시와 중복하지 않는다.
- 기기 알림 허용은 사용자 버튼으로만 요청한다. 브라우저 지원, iOS 홈 화면 설치, VAPID/발송 스케줄러, 실제 기기 수신은 서로 다른 검증 항목이다. Native APNs/FCM 구현을 Web Push 완료로 부르지 않는다.
- 실제 금융 공급자 확인·운영 정책이 연결되기 전에는 `checkoutEnabled:false`를 유지한다. 테스트용 confirmed receipt와 실제 거래 증거를 구분한다.

실행 묶음: (1) R06/R07/R18 일반 모임 신청·승인 서버 및 양쪽 UI (2) R08/R19 공통 기기 알림 (3) R15 본인 연애 상태 요약 (4) 회귀·독립 보안 검토·캡처. R01–R17의 나머지 콘텐츠/원장/운영 목표는 앞선 상세 보고서 번호를 유지하며, 이번 묶음 완료와 전체 완료를 혼동하지 않는다. 원격 적용·실결제·실제 사용자 발송·Git 반영은 실행하지 않는다.

- 일반 사용자 개설 모임의 목록·상세 → `/meetups/[id]/apply` 연결, 소개 → 보증금 → 상태 확인 React 화면 구현.
- 보증금은 첫 단계 안내 및 두 번째 필수 단계에 노출. 새 결제와 이월 버튼 문구를 구분한다. 이월은 UI 예시만 제공하며 실제 신규 서버 계약은 아직 허용하지 않는다.
- 준비 API는 본인·모임에 묶인 정책 견적과 미납 준비 기록만 만든다. `checkoutEnabled:false`, `applicationId:null`, `draft/unpaid`가 강제된다. 실제 화면은 PG 콜백을 연결하지 않아 결제·접수할 수 없다.
- 후속 R18 구현으로 신뢰된 서버 영수증 확인 이후에만 유료 신청을 만드는 별도 lifecycle을 추가했다. 기존 방 공지·방장 개인/멤버 알림·승인 멤버십·이전 대화 열람·거절/취소/탈퇴의 반환 대기 기록을 연결했다. 공급자 영수증 검증과 실제 결제/환불 실행기는 남아 있으므로 `refund_due`를 환불 완료로 표현하지 않는다.
- R19 공통 Web Push 구독·전송 대기열·발송기와 모임 계열 6종 채팅 메시지 알림을 추가했다. 실제 VAPID/스케줄러/기기 수신 미검증, 매칭·친구 DM 새 메시지 발행원과 네이티브 APNs/FCM은 남은 일이다.
- R15 본인 연애 상태 요약을 홈·매칭 진입에 추가했다. 실제 Auth가 없는 로컬 리허설과 계약 시험 근거이며 실계정 홈 표시를 확인한 것은 아니다.
- 스터디·멘토링의 개설자 승인 전환, 전공 데이터 확충, 전체 활동 원장·운영자 반환·이월·출석 분쟁·공동 맛집 통계·학과 심벌은 이번 일반 모임/알림 묶음 완료에 포함하지 않는다. 최신 상태는 `artifacts/qa/20260912-admission-awareness/REPORT.md`의 R01–R19 표를 따른다.
- 이전 custom 가입 HTTP POST는 409로 차단, 새 migration 후보는 직접 가입 RPC 실행 권한을 철회한다. 기존 참가자의 나가기·채팅은 유지. 원격 migration은 미적용이므로 원격 우회 차단 완료가 아니다.
- `/meetups/dev-application`은 development + offline-ui 서버 조건에서만 제공되는 앱 내 리허설이다. 표시 금액·참가자·납부/승인 결과는 가상 예시다.

## 후속 구현 계약 — 스터디·멘토링 승인 모집

사용자의 “ㅇㅇ 구현해봐”에 따라 G2/R06·R07·R18의 다음 묶음을 진행한다. 전체 R01–R19 완료나 원격 적용 승인이 아니다.

1. 기존 스터디의 과목·10회차 안내·일정 투표·대화·나가기·신고를 유지한다. 새 방만 이름과 개설자를 지정해 만든다. 과거 방에 임의로 방장을 배정하지 않는다. 기존 참가자는 기존 방을 계속 열 수 있다.
2. 멘토링은 사진 역할 선택 → 이름 있는 모집방 → 보증금 포함 신청 → 개설자 수락 → 채팅이다. 역할은 경험 나눔/도움 구함, 목표는 2+2 또는 3+3. 자동 조합 대신 각 역할 자리 수를 서버가 확인한다. 기존 제안·동의·활성 대화는 보존한다.
3. 두 종류 모두 같은 결제 영수증·보증금 원장을 사용한다. 방/사용자/멘토링 역할을 견적과 신청에 고정하고 영수증 재사용, 중복 참가, 마지막 자리 경쟁, 다른 학과·다른 방 접근을 막는다. 기존 일반 모임 RPC는 보존한다.
4. 새 신청 경로는 `/meetups/participation/[study|mentoring]/[id]/apply`, 관리 경로는 같은 경로의 `/applications`이다. 승인 후 채팅은 `/chat/rooms/study_room/[id]` 또는 `/chat/rooms/mentoring/[id]`로 연결한다. 일반 방 공지에는 소개·장점을 노출하지 않는다.
5. 승인된 디자인 언어(활동 사진, 여백, 짧은 단계, 큰 주요 버튼)를 재사용한다. 예시 화면과 실제 서버 화면을 명확히 구분한다. 실제 정책/PG 미연결은 보증금 미설정·결제 미연결로 표시하며 무료나 접수 완료로 바꾸지 않는다.

소유 범위: 서버 작업 A는 study/native admission 계약·API·마이그레이션·회귀 테스트, 서버 작업 B는 hosted mentoring 계약·API·채팅 권한·회귀 테스트, 주 작업자는 기존 UI 확장·공통 신청 표시·페이지 연결·브라우저 검증·보고를 담당한다. 독립 검토자는 동일 고정 후보의 권한·정원·금융 원장·구 UI 회귀를 재검토한다.

완료 근거: 실패를 먼저 확인한 회귀 테스트 → 구현 → 타입 검사와 대상 회귀 → 390px/데스크톱 클릭·캡처 → 고정 후보 독립 검토. 실제 Supabase Auth, 전체 migration 적용, 실결제/환불/이월, 실제 휴대폰 수신은 별도 미검증으로 유지한다. Git stage/commit/push·원격 변경·배포는 하지 않는다.
