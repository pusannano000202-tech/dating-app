## 발견한 문제와 수정 내용

- 기존 CTA는 활동별 방이 아니라 같은 카테고리 목록을 다시 보여주고 수동 방 개설을 제안했습니다. 자동 모집방 전용 동선으로 수정했습니다.
- 정원·방 번호·참여 여부를 화면에서 추정하지 않고 서버 계약으로 검증합니다. 연결 실패를 `방 0개`나 가짜 참여 성공으로 표시하지 않습니다.
- 누가 나가면 **그 방을 그대로 재모집**합니다. 예를 들어 `1번 5/5 + 2번 2/5 → 1번에서 한 명 탈퇴 → 1번 4/5 + 2번 2/5`이며 둘 다 유지합니다. 신규 회원이 1번에 들어가면 `5/5 + 2/5`가 됩니다. 이때 2번 방을 닫거나 인원을 합치지 않고, 빈자리가 있으므로 불필요한 3번 방만 만들지 않습니다. 정원 초과 방지를 위한 잠금은 이 동작을 막는 것이 아닙니다.
- 차단된 상대가 있으면 참여를 거절합니다. 채팅을 열 수 없어진 경우에도 자신의 방 참여를 취소할 수 있는 별도 버튼을 제공합니다.
- 현재 학교·성별·계정 정지/삭제·프로필 상태를 조회/참여/채팅에서 다시 검사합니다. 직접 테이블 접근은 막고 인증된 서버 함수만 허용합니다.
- 메시지 재전송은 중복 저장하지 않습니다. 처음에는 최신 100개를 읽고, `이전 대화 불러오기`로 더 오래된 대화를 100개씩 읽습니다. **새 참가자도 가입 전에 작성된 약속을 확인**할 수 있습니다. 단순히 방을 나갔다고 그 사람이 쓴 기존 대화를 삭제하지 않습니다. 사용자당 분당 30개 전송 제한은 유지합니다.
- 로그인 후 돌아갈 주소 파라미터, 통신 시간 초과, 오래된 응답의 덮어쓰기, 존재하지 않는 방을 서버 장애처럼 설명하던 문구를 수정했습니다.

## 남은 위험 또는 미검증 사항

1. **실제 DB 반영 필요:** 현재 3013 앱이 사용하는 로컬 서비스의 새 RPC는 준비되지 않아 방 API가 503입니다. 신규 파일 하나만 무조건 적용하지 않고 기존 선행 migration 적용 상태·데이터 보존·복구 방법을 확인한 다음, 별도 승인 범위 내에서 적용해야 합니다. 데이터 초기화는 하지 않았습니다.
2. DB 반영 후 서로 다른 학교·성별·차단·정지 계정 및 최소 6개 테스트 계정으로 정원, 다음 방, 재접속, 실제 메시지 저장을 검증해야 합니다. 여러 DB 연결이 동시에 마지막 자리를 요청하는 상황은 미검증입니다.
3. 실제 휴대폰에서 가로 넘기기, 키보드 열린 상태, 네트워크 끊김·재연결, 뒤로가기 검증이 필요합니다.
4. 이번 브라우저 검수에서 `나가기`의 네이티브 확인창이 자동 제어를 중단시켜 해당 클릭 흐름의 종단 검증은 제한됐습니다. SQL의 나가기·차단 후 자기 탈퇴는 행동 시험으로 검증했습니다.
5. 오래된 채팅 페이지 넘김은 후속 사용자 교정에 따라 구현 범위에 포함했습니다. 운영자용 방 종료·보관 화면과 무기한 운영 정책은 여전히 별도입니다.
6. 원격 DB·운영 RLS·배포·실계정 검증은 수행하지 않았습니다. 이 보고는 운영 출시 승인 보고가 아닙니다.

## 후속 교정: 빈자리 재모집·입장 전 대화

앞선 44줄은 “모집 중인 방을 한 개만 유지한다”는 의미가 아니었으나 설명이 모호했습니다. 위 항목을 정확한 `4/5 + 2/5` 사례로 바꿨습니다. 기존 SQL에서 동시에 재모집되는 동작을 회귀 시험으로 확인했고, 실제 빈틈이었던 100개 이전의 대화 조회를 추가했습니다.

- 추가 SQL 파일: `supabase/migrations/20260907121222_activity_room_history.sql` (실제 DB 미적용).
- `GET /api/meetups/rooms/{roomId}/messages`: 매 요청 현재 참여 권한을 확인하고, 정밀한 시각+메시지 ID로 중복/누락 없이 이전 페이지를 조회합니다.
- 브라우저 예시 데이터: 100개 → 이전 페이지 클릭 → 105개, 첫 약속 “오늘 저녁 8시, 부산대 정문 앞에서 만나요.” 확인. 기존 첫 메시지 위치를 유지했고 주기적 갱신 뒤에도 105개가 유지됐습니다. 답장 뒤에는 106개이며 첫 약속도 유지됐습니다.
- 수동 새로고침은 최신 100개로 돌아가 이전 대화 버튼을 다시 제공합니다. 삭제 등으로 유효하지 않게 된 커서도 이 방법으로 복구합니다. 동일 시각 메시지 201개를 100+100+1로 빠짐·중복 없이 읽는 SQL 시험을 포함했습니다. 후속 변경을 포함한 Next 빌드도 214/214 페이지 생성 및 타입 검사까지 통과했습니다.
